Wave 06 Cycle 02. This ticket is the onboarding Cycle of the approved Pull-Request Mode RFC (docs/RFC/pull-request-mode.md, merged as 0db9124d), section "Onboarding and setting changes"; decisions 8, 9, 15, 19 and 21. It now depends on vh-c2dtj (Wave 06 Cycle 01: the setting, the link builder and pull-only repo sync).

The RFC settles the questions this ticket left to planning:

- While the setup branch is unmerged, nothing works on the repository. Item writes answer `setup_pending`, and `repo list` and `repo inspect` show the repository waiting, with the link.
- A poll learns of the merge when the remote's primary holds a valid `.manyhands/config.toml` with the same primary branch. It fast-forwards the local primary and deletes the local setup branch. If the merged configuration differs, the merged one wins.
- The publication remote selection goes in the same setup commit as the configuration.
- `repo enable` and Add repository take the mode. The default is pull-request mode for a recognised or configured forge (decision 9), and `repo create` keeps its direct commit.
- The remote's primary must exist (`remote_primary_missing` otherwise).

Scope added by the RFC: in an enabled repository, a change to the mode, the forge or the publication remote goes through a setup branch the same way, and close and promote refuse with `setup_pending` until it merges. A pending setup or change can be abandoned or cancelled, which deletes the setup branch locally, and on the remote if it is still at its published tip. The setup branch is `manyhands/setup/<ULID>`. Polling a repository whose setup is pending runs on the pending remote selection, which is new work: today a poll needs a valid configuration that names a remote.

Teammates who clone before the merge see no configuration, and after it they onboard as a clone does today. This ticket's acceptance stands, together with the onboarding tests in the RFC's Testing section.
