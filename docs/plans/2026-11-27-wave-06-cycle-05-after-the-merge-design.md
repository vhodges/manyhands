# Wave 06 Cycle 05 Design: After The Merge

Cycle document: [Wave 06 Cycle 05](../Cycles/wave-06-cycle-05-after-the-merge.md). Ticket: vh-ssepw (`01M876851FT3NPSH9KDXKXR1AJ`). Authority: the [Pull-Request Mode RFC](../RFC/pull-request-mode.md), the Cycle document's Product-Owner Decisions, and [Wave 06 Cycle 04](../Cycles/wave-06-cycle-04-pull-request-promote.md) and [Cycle 03](../Cycles/wave-06-cycle-03-pull-request-close.md), whose lifecycle paths, content-proof rule, retirement fence, link record and `unheld` list this Cycle builds on.

Status: **draft**, revision 3, for review. Not approved. Revisions 1 and 2 had two independent reviews each (Review Record); revision 3 applies the second round and the owner's decision 11, and has not been reviewed yet.

## Intent And Approval Boundary

After a pull request merges on the forge, in any style, record when each item reached the primary, report it from the poll that brought it with the dependents it made ready, tell every context whose item is done from one in progress, and end such a context through a confirmed `context cleanup`, a cleanup-only path of the close and promote lifecycles that deletes a surviving remote branch only at the tip it observed and shows what the primary does not hold before the person confirms. End a ticket's pull request link once the primary holds its closure. Warn when the registered checkout is not on the primary. Approving this design approves the Cycle document's Required Contract and the rulings below. It does not authorize implementation, pushes other than the ticket branch, or merging.

## Conventions

- Names are cited as `file` and `function`. Line numbers are approximate, at `0213d32d` (main `15ea8eb5` merged into the ticket branch). Task 0 re-checks every one.
- "The local primary" is `refs/heads/<primary>`. "The tracking primary" is `refs/remotes/<publication remote>/<primary>`, as last fetched.
- "The branch" is `manyhands/ticket/<ULID>` or `manyhands/document/<ULID>`. "`L`" is its local tip. "`R`" is its remote tracking tip, when that ref exists.
- "A move" is a change of the local primary by `integration/artifacts.rs` `fast_forward`, from "`before`" to "`after`".
- "The proof" is `context_retirement/proof.rs` `preservation` (Baseline Fact 8), against the local primary. "Done on the primary" is, for a ticket, a closure in the local primary's copy of its file; for a document, the proof of `L` against the local primary. Cycle 04's R-3 judges a document against the tracking primary as well; this Cycle reads the local primary only, because the RFC's decision 11 makes detection wait while the root is off the primary (R-27).
- "An arrival" is an item whose done state a move brought: a ticket whose closure, or a document whose content, `after` holds and `before` did not (Part A).
- "A cleanup record" is a `ticket_closures` or `document_promotions` row of the new action `cleanup` (Part E).

## Part A: The Arrival Record

**The table.** `src/repository/item_merges.rs` (a new module, beside `pull_request_links.rs`) owns `item_merges`, created by `discovery.rs` `migrate_item_merges` after `migrate_pull_request_links`, on `migrate_pull_request_links`'s pattern, with the marker `wave_06_item_merges_v1`:

```sql
CREATE TABLE item_merges (
    repository_id INTEGER NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
    kind TEXT NOT NULL CHECK(kind IN ('ticket','document')),
    item_ulid TEXT NOT NULL,
    commit_oid TEXT NOT NULL CHECK(length(commit_oid)=40 AND commit_oid NOT GLOB '*[^0-9a-f]*'),
    merged_at INTEGER NOT NULL CHECK(typeof(merged_at)='integer' AND merged_at BETWEEN 0 AND 253402300799),
    operation_ulid TEXT NOT NULL,
    PRIMARY KEY(repository_id, kind, item_ulid))
```

It survives `index rebuild` and goes with `repo remove` (Baseline Fact 22). Its functions, each added in the task that first calls it: `record(tx, repository_id, operation, &[Arrival])`, an upsert per item, so a later arrival of the same item (a document promoted again) replaces the row, unless the row's commit is not an ancestor of the new one (two sites recording out of order), when the row stays (R-37); `merge_of(connection, repository_id, kind, item) -> Option<ItemMerge>`; `merges_by(connection, repository_id, operation) -> Vec<ItemMerge>`.

**The rule (R-1 to R-4).** `item_merges::arrivals(repository, before, after) -> Result<Vec<Arrival>, git2::Error>`:

1. Nothing when `before` equals `after` or is not an ancestor of it.
2. The candidates: `diff_tree_to_tree(before's tree, after's tree)`, with no rename detection, keeping the paths added or modified at `after` that are a ticket's file (`.manyhands/tickets/<ULID>/ticket.md`) or a Markdown file under `docs/`. A ticket is a candidate when its `after` copy parses with `closed_at` and its `before` copy is absent, does not parse, or has no `closed_at` or another one. A document is a candidate when its `after` copy parses as a managed document, which gives its ID; a move counts, since its new path is added. A managed document deleted at `after` (present at `before`, absent anywhere at `after`) is not an arrival: its row is deleted (R-37).
3. The walk: a `Revwalk` that pushes `after`, hides `before` and simplifies to first parents, newest first. Each commit is diffed against its first parent (the empty tree for a root), restricted by a literal pathspec to the candidates' paths not yet assigned. The first commit that changes a candidate's path assigns it that commit and its committer time. The walk stops when every candidate is assigned or the commits run out.
4. An unassigned candidate (its change came only through a commit `before` holds) is dropped (R-4).

Only the range's first-parent commits are diffed; marking `before`'s ancestry is libgit2's (Baseline Fact 2). A test-only counter of commits diffed, `item_merges::take_diffed`, as `activity.rs` has one, lets P2 pin each row's exact count, never more than the range's first-parent commits.

**Recording (R-5, R-6).** `item_merges::record_after_move(service, root, operation, before, after)` computes the arrivals and records them in one Immediate transaction, once a move has succeeded, outside the move's own transaction; a failure to compute or record is dropped, with no row, and never changes the verb's answer. The calls:

- the poll: in `poll_after_fetch_into`, after the primary target's `poll_fast_forward_unlocked` answered `FastForwarded`, with `owner.operation_id()` (Baseline Fact 1);
- `repo sync` and a lifecycle's primary child: `reconcile_pending_candidate`, both stages of `integrate_divergence` and `synchronize_remote_observed_inner`, for a `Primary` target, with the synchronization's operation ID;
- a direct close's or promote's integration: the runner after `L::apply` answered `Integrated::Merged`, with `before` read as `prepared.evidence().old_primary` before `write_commit` and the record's operation ID;
- a setup's activation: `setup/poll.rs` `activate` after its move, with a new `OperationId` (it has none, Baseline Fact 1).

A resume that skips the move, `conflict resolve`, and a move made outside Manyhands record nothing (K-1, K-3). The activation is a Manyhands fast-forward of the local primary and records, as decision 2 asks of every one (R-6).

## Part D: Detection Per Context

Each poll classifies a context, after the primary moved (Baseline Fact 4), by this table. "Equal" is `classify_local_target`'s `current`, read before any move of that context in the same poll; a context the poll fast-forwards reads `fast_forwarded`, and the next poll classifies it. "Held" is a cheap pre-filter (R-12): for a ticket, the local primary's blob at its path parses with `closed_at`; for a document, the local primary's blob at its path equals `L`'s. "Proof" is `preservation(L, local primary)`, run only when held.

| Kind | Remote branch | `L` against `R` | Held | Proof | Disposition |
| --- | --- | --- | --- | --- | --- |
| ticket | observed deleted | — | yes | passes | `closed`, as today |
| ticket | observed deleted | — | yes | `ContentMismatch` | `unheld` (new; today `closed`) |
| ticket | observed deleted | — | yes | undecidable, or `L` unreadable | `closed`, as today (K-14) |
| ticket | observed deleted | — | no | — | `remotely_deleted`, as today |
| document | observed deleted | — | — | passes | `promoted`, as today |
| document | observed deleted | — | — | fails | `remotely_deleted`, as today |
| ticket | present | equal | yes | passes | `merged` (new) |
| ticket | present | equal | yes | `ContentMismatch` | `unheld` (new) |
| ticket | present | equal | yes | undecidable | `current`, as today (K-14) |
| document | present | equal | yes | passes | `merged` (new) |
| document | present | equal | yes | fails | `current`, as today |
| either | present | equal | no | — | `current`, as today |
| either | present | any other | — | — | as today |

- "Undecidable" is a proof refused as `ShallowHistory`, `MissingObject`, `UnrelatedHistory`, `MultipleMergeBases` or `InvalidPrimaryItem` (decision 8: only a real content mismatch gives `unheld`).
- A document is never `unheld`: the poll cannot tell a squash the primary moved on from an edit in progress (R-12, K-6).
- Retirement still acts on `closed` and `promoted` only (Baseline Fact 5), so `merged` and `unheld` are never retired by a poll, `context retire` or the desktop; their way out is `context cleanup`.

- While the root is off the primary or not clean the primary does not move, so nothing new reads `merged`, `unheld`, `closed` or `promoted` and nothing is recorded; once the root is back, the next poll moves the primary, records and reports (the RFC's "detection waits").

## Part E: `context cleanup`, A Cleanup-Only Lifecycle Path (Decisions 1, 3, 7 And 11)

`context cleanup --repo R --id I`, with `--prepare`, `--confirm <ULID>` and `--request-id`, no input and no `--kind`. For a ticket it is a `ticket_closures` record and for a document a `document_promotions` record, of the new action `cleanup`, run by the shared runner through a third path that reuses the direct cleanup step's parts (Baseline Facts 12, 13 and 17) with no context child, no integration and no publication, and with its own handling of stops (decision 7). It works the same in either mode (R-25).

### What It Changes

1. **The records.** `ticket_closures.action` gains `cleanup`; `document_promotions` gains an `action` column (`promote` or `cleanup`, `promote` for every existing row). A cleanup record has a third `RecordPath`, `Cleanup`, in both tables, whatever its `integration_mode`, which records the repository's mode at begin and changes nothing (R-33); the exhaustive matches on `RecordPath` gain its arm. It stores at begin, immutably, the consented `L`, `R` (or none), a digest of its `unheld` list, the publication remote's name and endpoint digest and the primary branch. Its steps are `confirmed`, `remote_deleting` (new: saved once the delete may be sent), `remote_deleted`, `worktree_removing`, `worktree_removed`, `branch_deleted` and `complete`, or `abandoned`. A cleanup record is never superseded, and its begin supersedes nothing: every unfinished record of the item, supersedable or not, holds a cleanup's prepare (CC3) (R-33). Each table is rebuilt once, one way, with a frozen copy of today's schema and an explicit column list, as `wave_06_closure_modes_v1` and `wave_06_promotion_modes_v1` were, under the new markers `wave_06_closure_cleanup_v1` and `wave_06_promotion_cleanup_v1`, inside `migrate_registry`'s first transaction (R-28).
2. **The runner's third path.** For a record at `confirmed`, on its first run and every re-run: re-check the consent (`L`, `R`, the `unheld` list, the remote's name and endpoint, the primary branch, the blockers, and the configuration's validity), and end the record refused on a difference (CC10). With a publication remote: reserve the item's context with the kind's action (`close` or `promote`), by `reserve_remote_operation` the first time and `restart_remote_lifecycle` after; pass `BeforeTransport`; run the head check and the full check against the consented `L` (CC12). With `R` set: inside `PromotionIo::delete`, after its `AfterAdvertisement` safe point and before `delete_exact`, save the record's step as `remote_deleting`; `PromotionIo::delete` reports an absent branch as `Absent`, apart from `Deleted` (CC13 to CC15). With `R` unset: a new advertisement-only `PromotionIo` method, which `FakeIo` scripts too, reads whether the branch is advertised (CC16). For a record at `remote_deleting`, a re-run skips the consent re-check and observes again (CC21). Then the local removal at the consented `L`, the tracking ref's deletion with `R` (or none) as its expected value, and `complete_record` retiring at `L` (CC17). `merged_context` and `make_outcome` learn the cleanup record (Task 8).
3. **Its stops.** An end refused before the delete is the record `abandoned` with the refusal `external_change`; when a reservation is held, the runner then passes `AfterAdvertisement` without advertising and ends the reservation with `finish_parent` as `cancelled`, as Cycle 03's new branch ends its own (Baseline Fact 18). A reservation that is busy answers `busy` with nothing held. A transport, key or host stop, a refused delete and a stopped local removal keep the record unfinished and the reservation held, as the direct cleanup keeps them (CC19, CC20, CC23).
4. **The binding.** One CLI verb over two lifecycles: `Command::ContextCleanup` binds `CleanupTicket` or `CleanupDocument`, a `LifecycleVerb` each, by the item's kind, with the cleanup's own data and preview shapes, as `ticket withdraw-closure` is a verb of its own over `ticket_closures` (Baseline Fact 14). Every list keyed by command learns it, resolving the kind from the record where it dispatches by command: `LIFECYCLE_COMMANDS`, `progress.rs`'s `asks_a_parent` and `cancel_parent`, `setup/change.rs`'s accepted lifecycle requests (about 499-525), `bind/mod.rs` `recorded_effects`, `replay.rs` (about 200-209), `way_out.rs` (about 132-136) and `bind/resume.rs`. `operation list` lists it with its kind's remote action and the command `context cleanup`.
5. **The holds.** A new predicate, any unfinished cleanup record of the item at any step in either mode, holds every lifecycle prepare of the item (CC3) and every retirement path (CC28: the poll's capture and its skip of a ticket context, `context retire`'s claim and its backstop, and the desktop's retirement), beside `written_closure_holder` and `pull_request_promotion_holder` (U-5).
6. **Abandon** (decision 11). `operation abandon` reaches a cleanup record, and only a cleanup record, at any unfinished step, when no live process runs its request: it acts as a re-run of that request that ends it, taking the reservation over with `restart_remote_lifecycle` when one exists, passing both safe points without a connection, and, in one transaction, marking the record `abandoned` and ending the reservation with `finish_parent` as `cancelled`. `reservation::abandonable` and `mutation/bind/abandon.rs` learn the cleanup record, which `abandon.rs` finds in the lifecycle tables even with no remote row (U-6).
7. **The remote reservation's changes,** and only these: `finish_parent`'s join for a cleanup record, completed or `cancelled`; `abandonable` for a cleanup record. Task 7's checkpoint stops for the owner if the mechanism needs any other change to the reservation's rules, a new remote action, a change to the transport, or a change to the conflict verbs.

## Rulings

Each: decision — why — cost if wrong.

- **R-1** One function decides the arrivals of every move — decision 2 — a fault reaches every site at once, which P2's table pins.
- **R-2** A ticket arrives when its `after` copy has `closed_at` and its `before` copy has none; a document when its file is added or modified at `after` — the RFC's done states, a closure and the content — a document moved without a change of content arrives again.
- **R-3** `merged_at` is the committer time of the newest first-parent commit in the range that changed the item's file — it is the merge, squash or fast-forwarded commit the RFC names, by one rule for both kinds and with no blob read per commit — for a fast-forward it is a branch commit's time (K-2), and for a ticket saved after its closure on its branch, the save's.
- **R-4** A candidate that no commit of the walk changed gets no row — the walk never leaves the range — a rare arrival with no time.
- **R-5** Recording follows a move that succeeded, outside its transaction, and a failure is dropped — `merged_at` is for display, and a move must never fail for it — K-3.
- **R-6** Every move of Baseline Fact 1 records, a setup's activation included as a Manyhands fast-forward, and a resume that skips the move or `conflict resolve` does not — decision 2 — K-1 and K-3.
- **R-7** A ticket's time is on its closure and a document's on the item, both filled only by `show` and `show --path`, after the staleness comparison — the RFC's places, and lists read the index only — the desktop's lists show none until Cycle 06 asks for them.
- **R-8** The poll's `merged` list is the rows its own operation recorded, not carried in `RemotePollReport` — the report's frozen image, its replay from the table and its equality have no place for it (Baseline Fact 7) — a replay whose stored answer was lost rebuilds the list from rows a later arrival may have replaced, and a poll that stopped after its move lists nothing (K-3).
- **R-9** `made_ready` and its state as a direct close gives them, read after the poll's refresh, with only `current` and `index_pending` — one vocabulary — none.
- **R-10** A ticket's `closed` needs the proof as well as the closure, and only `ContentMismatch` gives `unheld` — decision 8 — none beyond decision 8's.
- **R-11** `merged` and `unheld` enter the registry through a new frozen catalog, upgraded one way as `unpublished` was, by Part D's truth table — the CHECK lists every value (Baseline Fact 6) — one more one-way migration.
- **R-12** Detection runs the proof only past the cheap pre-filter, and never gives a document `unheld` — a check per context per poll must not read whole trees for items in progress, and a document's proof failure is also an edit in progress — a document done at another path (moved on the primary) reads `current`.
- **R-13** `merged` and `unheld` only for a context whose `L` equals `R` before any move of it in that poll, or whose branch is gone — the poll does not choose between a branch's local and remote commits — K-9.
- **R-14** The desktop gets compile-level arms only — Cycle 06 — the desktop shows `merged` and `unheld` as it shows `current` until then (K-13).
- **R-15** No new SSH case: Cycle 03's case gains the cleanup steps — AGENTS.md; the deletion is this Cycle's only transport-dependent part — that case runs a little longer and fails for three Cycles' regressions.
- **R-16** `repo inspect`'s check is the poll's own guard — the warning must say exactly when a poll cannot move the primary — inspect reads an index unequal to `HEAD`'s tree as `primary_dirty`.
- **R-17** The warning for a repository whose registry records a publication remote, or which has a pending setup, with the primary from the registry or the setup record — no poll runs without a remote, a setup's activation waits for the checkout too (the RFC's "Checkout not on the primary"), and the working tree's configuration is the checked-out branch's — a remote-less repository off its primary is not warned (K-15).
- **R-18** `poll once` warns in human output; its JSON keeps the primary's disposition — the disposition already says it, the desktop's row is Cycle 06's, and the skill tells a JSON reader to run `repo inspect` — a JSON reader needs a second call.
- **R-19** `context cleanup`'s behaviour is the CC table, its shape is Part E's "What It Changes", and its remaining mechanism is Task 7's checkpoint's — Cycle 04's re-run and fence mechanisms were settled only against outcome tables after three review rounds, and two rounds here found the reused step's stops other than assumed — the remaining mechanism is reviewed at the checkpoint, posted on the ticket, and in Tasks 7 to 10's reviews.
- **R-20** The cleanup's blocked prepare reuses `LifecycleBlocker` and `LifecycleBlockedDto`, adding `not_done_on_primary` — one blocker vocabulary for the lifecycle's verbs — close's and promote's blocker schema lists a value they never give.
- **R-21** The cleanup needs the root on a clean primary and the context clean, as a direct close's prepare does — its local retirement needs both (Baseline Fact 8) — the person cleans up first.
- **R-22** `unheld` is empty when the proof passes and `unheld_entries(L, local primary)` when it fails — Cycle 03's list, while `unheld_entries` lacks the proof's ticket-file exception (Baseline Fact 8) — none.
- **R-23** A remote branch that moved since the last fetch is not deleted, and confirm answers `external_change` — decision 22's guard by the observed tip — the person polls and prepares again (K-11).
- **R-24** The cleanup's reservation is the direct cleanup's, held from before its delete until its retirement ends, except where Part E item 3 ends it on a refusal — decision 7 — a cleanup stopped once reserved holds the repository until it finishes or is abandoned (K-12).
- **R-25** The verb works the same in either mode — retirement does, and a direct context can need it — none.
- **R-26** Times are RFC 3339 UTC in whole seconds, as `closed_at` — one format — none.
- **R-27** Detection and the cleanup judge a document against the local primary only, not Cycle 04's R-3 with the tracking primary — the RFC's decision 11 makes detection wait while the root is off the primary, and the cleanup's local retirement needs the local primary — while the root lags, `document show` (R-3) can read a document held that the poll does not yet report.
- **R-28** The two lifecycle tables are rebuilt once each, one way, in the first transaction, as Cycles 03 and 04 rebuilt them — decision 7 — two more one-way migrations, pinned by E-15 and E-16.
- **R-29** A cleanup record retires at its consented `L`, which `finish_parent`'s join and `complete_record` match — the direct cleanup retires at its merged context, which a cleanup record does not have — none.
- **R-30** `context cleanup` is refused before a first-time setup only, as `context retire` — it acts the same in either mode, unlike close and promote, which a pending change refuses because they would act in the old mode — none.
- **R-31** With a publication remote, the cleanup always reads a fresh advertisement before it retires, also when the last fetch saw no branch — the contract's "Completed-context retirement" requires fresh authenticated evidence of absence (Baseline Fact 8) — a connection where the preview promised none.
- **R-32** `context cleanup`'s recoverable answers use the Request finality table, as `context retire`'s do, with no row in the six-family Recovery tables — the contract's sentence about 1410-1416 — the human lines and way outs are pinned by unit tests, not by recovery-table goldens.
- **R-33** A cleanup record has a `RecordPath` of its own, is never superseded and supersedes nothing — `supersedable` and `begin_retiring` act on direct records in cleanup categories, so a stopped cleanup would otherwise be replaced by a `document promote` or replace a stopped close — a stopped direct close or promote of a done item blocks its cleanup until it is finished or superseded by its own verb.
- **R-34** A refusal before the delete ends the record `abandoned` with `external_change` and, with a reservation held, ends the reservation as `cancelled` after passing `AfterAdvertisement` without a connection — Cycle 03's new branch ends its reservation so, and a refused cleanup must not hold the repository — the direct cleanup's own stops keep the reservation, so the third path maps its stops itself (Part E item 3).
- **R-35** A cleanup saves `remote_deleting` before its delete may be sent, and a record at that step re-runs with no consent re-check and reads an absent branch as `deleted` — nothing else records that a delete may have gone out (`delete_exact` answers `Sent` on a rejection or a lost connection) — one step more in each rebuilt table.
- **R-36** `operation abandon` ends a cleanup record as a re-run of its request that ends it, taking over its reservation with `restart_remote_lifecycle` and ending it with `finish_parent` as `cancelled` — decision 11, and `finish_parent` needs the reservation's own owner at `AfterAdvertisement` (Baseline Fact 13) — an abandon that finds a live run answers `busy`.
- **R-37** A ticket arrives again when its `closed_at` changes, a deleted document's row is deleted, and an upsert keeps a row whose commit the new one does not descend from — the record must describe the primary's current copy, and two sites can record one item out of order — an ancestry check per recorded item.
- **R-38** A retiring poll's `merged` list and its `made_ready` are frozen with its summary — `pass_report.rs` `finish` returns the frozen summary on every later call (Baseline Fact 7) — `made_ready` reads the index as the retirement children left it, before or after their retirements, which do not change readiness.

## Alternatives Rejected

- A confirmed mode of `context retire`, or two verbs: decision 1.
- Recording at the poll's move and the direct integration only, or from a stored watermark at every index observation: decision 2.
- Allowing the manual cleanup for any published document context: decision 3.
- Deleting a surviving setup branch: decision 4.
- A `synchronize_context` reservation, or an own record with no reservation, with or without an item hold: decision 7; the first cannot be reserved, finished or resumed as a cleanup (Review Record), and the others would leave a republished branch, or need holds in the reservation and the writers.
- Abandon only before a delete may have been sent: decision 11; a remote that can never be observed again would leave the repository's local writes blocked for good.
- Letting a cleanup supersede a stopped direct record, or be superseded: R-33.
- Carrying `merged` in `RemotePollReport`: R-8.
- No new dispositions, so that only the poll that brought an item flags it: a context that needs cleanup would be flagged once and then read `current` on every later poll.
- `PrimaryActivityMap` as the source of `merged_at`: it advances at indexing, rebuilds when its base is off the first-parent chain, and loses its base at an index rebuild (Baseline Fact 2).
- The local retirement before the remote deletion: a poll between them would materialize a squash-merged branch again (Baseline Fact 4).
- A new remote action value: a table rebuild with foreign keys pointing at it.
- A new SSH case: R-15.

## Risks

| Risk | Mitigation |
| --- | --- |
| A recording fault slows or fails a move of the primary | R-5: outside the move's transaction, dropped on failure; P3 asserts the poll's answer unchanged |

| A migration damages a real registry, one way | Frozen schemas, explicit column lists, Part D's truth table, P5's and P7's upgrades from tables holding rows, E-14 to E-16, all inside the first transaction as before |
| Detection slows every poll | R-12's pre-filter; the proof only for items done on the primary |

| `context cleanup` deletes a commit made after consent | CC10, CC12 and CC23: the consent re-check and head check before the delete, the compare-and-swap after; P7 |
| A stopped cleanup jams the repository | K-12, CC24 and CC26: the same request, or abandon at any step when no live run holds it; the skills say so |
| An abandon races a live cleanup | CC26 answers `busy` while a live process runs the request; the abandon acts as a re-run of that request (R-36); P7's abandon rows |
| The lifecycle's shared runner changes break a direct close, promote or a branch record | Every existing runner test, the `ticket_closure` and `document_promotion` targets, E-16's rows reading their old actions |
| Golden rewrites hide a regression | E-3 and E-4 are additive fields only; each rewrite's diff is read in the ledger |
