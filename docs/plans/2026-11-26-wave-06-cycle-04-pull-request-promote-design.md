# Wave 06 Cycle 04 Design: Document Promote In Pull-Request Mode

Cycle document: [Wave 06 Cycle 04](../Cycles/wave-06-cycle-04-pull-request-promote.md). Ticket: vh-rphcs (`01M87684C9GM9BJP5QQ429KMAK`). Authority: the [Pull-Request Mode RFC](../RFC/pull-request-mode.md), the Cycle document's Product-Owner Decisions, and [Wave 06 Cycle 03](../Cycles/wave-06-cycle-03-pull-request-close.md)'s design, whose branch records, link record and item field this Cycle builds on.

Status: **draft**, revision 4, 2026-11-26. Revisions 1 to 3 had independent reviews (Review Record); revision 4 has not been independently reviewed. Three rounds found blockers in the same two mechanisms (decisions 13 and 14), so revision 4 states them as required-outcome tables (RR and F) and makes Task 4 test-first against them, with a design checkpoint that chooses the mechanism, as the planning skill directs.

## Intent And Approval Boundary

In a pull-request repository, make `document promote` synchronize and publish the document's branch and answer with the pull request link, never committing to or pushing the primary; the only commits on the branch are the synchronization's own merges. Promoting again while the link is outstanding synchronizes again and answers `already_applied` with the same link. A document counts as promoted only when the content proof shows that a primary holds the branch's content, so a squash merge counts and an edit of a merged document does not count before its own pull request merges. The pull-request promote is a mode of the existing document-promotion lifecycle (decision 1). Approving this design approves the Cycle document's Required Contract and the rulings below. It does not authorize implementation, pushes other than the ticket branch, or merging.

## Conventions

- Names are cited as `file` and `function`. Line numbers are approximate, at `bef571fd` (Cycle 03's branch, which holds main `6c7937c8`); Task 0 re-checks every one after Cycle 03 merges.
- "Pull-request repository" means a valid configuration with `integration = "pull_request"` (Wave 06 Cycle 01), which is `format_version = 2` and always names a publication remote.
- "The local primary" is `refs/heads/<primary>`. "The tracking primary" is `refs/remotes/<publication remote>/<primary>`, as last fetched.
- "The branch" is `manyhands/document/<ULID>`. "`L`" is its local tip. "`R`" is its remote tracking tip, `refs/remotes/<publication remote>/manyhands/document/<ULID>`, when that ref exists.
- "The proof" is `context_retirement/proof.rs` `preservation` (Baseline Fact 11). "The primary holds the document" is the rule R-3 of Part B.
- "A link row" is the document's row in `pull_request_links` (kind `document`). "An outstanding link" is a link row while the primary does not hold the document (decision 3).
- "An active context" of a document is the one its read comes from when the index's row for the document has `context.kind` `active`: its own worktree on the branch.
- "A branch record" is a lifecycle record whose path is `RecordPath::Branch` (Cycle 03). "A pull-request promotion" is a `document_promotions` row whose `integration_mode` is `pull_request`. "A direct promotion" is today's.
- "A child that completed" is a context child whose synchronization finished (`published` or `already_current`). "A child that ended" is one that `ends_context_child` names, or a branch gone after its child (`BranchEnd`). "A child that stopped" is any other stop.
- "The consented tip" is `L` as the confirm's re-observation read it, stored in the record's own immutable column when it begins (Part A).
- "A refused record" is an `abandoned` row with a `blocked`, `external_change` or `reconfirmation_required` refusal and no answer: written by `refuse_record` when a confirm's revalidation fails, or by the runner's `abandon` of an existing row.

## Part A: The Record

**The rebuild (R-1).** `document_promotions` is rebuilt once by a named migration, marker `wave_06_promotion_modes_v1`, run in `promotion/record.rs` `migrate` after `promotion_refusal_blockers_v2`, by rename and copy with an explicit column list. Today's `SCHEMA` is frozen as `SCHEMA_V2`, and the `promotion_refusal_blockers_v2` step rebuilds from `SCHEMA_V2`, as Cycle 03 did for `ticket_closures`; the stored DDL holds no SQL comments, because it is compared exactly; the create path writes the new DDL and both markers. The table gains these columns, all null in direct rows; Task 1's design checkpoint confirms each against the RR and F tables of Part C before the one rebuild, and may drop one only by showing an outcome that does not need it:

| Column | Meaning |
| --- | --- |
| `integration_mode` | `direct` or `pull_request`, `NOT NULL DEFAULT 'direct'`: the mode the record began in, fixed for its life (Cycle 01 decision 11), Cycle 01's `Integration` |
| `answer_code` | a finished pull-request promotion's answer (Part C), written in the transaction that finishes it; a same-request re-entry and a replay whose envelope was lost answer from it |
| `consented_context_oid` | the consented tip, immutable, as Cycle 03's column of that name |
| `situation` | `first` or `again`, as consented, immutable |
| `primary_branch` | the configured primary branch at begin, so that a record whose child completed finishes without the live configuration (RR2) |
| `endpoint_digest` | a digest of the publication remote's fetch and push URLs and the forge setting at begin, as retirement records `endpoint_digest`, so that RR5 sees a changed endpoint and not only a changed name |

Existing rows read `direct`. A direct promotion is unchanged in every rule. A pull-request promotion:

- keeps `context_oid`'s rule unchanged: unset at `confirmed`, the branch as `context_step` reads it from `context_synchronized` on;
- moves `confirmed` → `context_synchronized` → `complete` after a child that completed, `confirmed` → `abandoned` after a child that ended, and `confirmed` → `abandoned` as a refused record when RR4, RR5 or RR7 end it;
- never holds `integration_oid`, `integration_kind` or `base_oid`, and never reaches `integrating`, `integrated`, `published`, `publication_pending`, `remote_deleted`, `worktree_removing`, `worktree_removed`, `branch_deleted` or `superseded`;
- at `complete` holds its context child's category in `publication_category` (`published` or `already_current`) and its answer;
- at `abandoned` after an ended child holds the refusal `reconfirmation_required` and its answer, as Cycle 03's `abandon_branch_record` stores them; as a refused record it holds its refusal and no answer;
- never holds a URL, a title or a body.

The answer CHECKs follow Cycle 03's (Baseline Fact 22): `answer_code` is required at a pull-request `complete`, allowed at `abandoned`, and absent elsewhere and in direct rows. A refused record written at confirm takes the confirm's mode. `PromotionStep::permits`, `validate` and `save_record` read the mode, and `save_record` keeps the four new columns immutable once set. The unique unfinished index keeps one unfinished record per document, of either mode. `PromotionRecord::path()` is `Branch` for `pull_request`, and `answered()` is `answer_code.is_some()`.

`answer_code` holds a new `PromotionAnswer`: `promoted` (`ok`), `already_promoted` (`already_applied` with the link), `primary_holds` (`already_applied` without a link), `remote_branch_deleted`, `history_unresolved` (`recovery_required` with that blocker) and `context_gone` (the branch gone, answered as Cycle 03 answers `ContextGone`).

## Part B: Prepare

**Dispatch (R-2).** `document promote --prepare` reads the configuration. In a pull-request repository the observation is the pull-request observation, whose digest's domain is `manyhands pull request promotion v1`; otherwise it is today's, unchanged. Promotion's observation type carries the mode and the pull-request facts to the runner and to `begin_record`, as the closure's `ClosureObservation` carries its path (Part G item 12). Confirm re-observes the same way. A same-request retry finds its record and continues it in the record's mode.

**The primary holds the document (R-3).** It holds it when the proof for the branch's tip passes against the tracking primary, or against the local primary when the local primary is the tracking primary or an ancestor of it; and `R` is absent, equal to the tip or an ancestor of it. A local primary ahead of or beside the tracking primary holds commits no one else has (in this mode Manyhands never commits there), so it is not used. `R` ahead of or beside the tip is another clone's work this clone has not merged, and the document is then not held; after a child that ended with `remote_branch_deleted`, `R` reads as absent, because the fetch does not prune it (Baseline Fact 22). The rule is one function, `primary_holds_document`, in `promotion/observe.rs` (so the proof's module does not change), taking the repository, the tip to judge, the tracking primary's OID (or none), the primary branch's name, the publication remote's name, the item, and whether to read `R` as absent. Every `ProofRefusal` reads as not held. Prepare, confirm and `item sync` (Part F) use it with the full proof; `document show` uses the cheaper twin of Part E (decision 9).

**Prepare reads local state only**, with no network, lease or write. In a pull-request repository it decides, in this order:

1. not a document: `not_a_document`, as today; no context: `context_missing`, as today;
2. the blockers below;
3. the primary holds the document (R-3 on `L`): `already_applied` at prepare, with no data and no record (R-4), as Cycle 03's withdraw prepare answers it. There is nothing to confirm; cleanup is retirement's;
4. the branch's remote history is `Deleted` (a fetch saw it published, then gone): blocked with `remote_context_deleted`, as today, whose way out is `item republish`;
5. a link row exists: the situation `again`;
6. otherwise: the situation `first`.

**The effects (R-24).** `first` and `again` preview `context_synchronized`, `context_published` and `pull_request_link`, as the RFC lists them: the synchronization may merge the remote's primary in and publish even when `L` equals `R`.

**The blockers** kept from the direct promote: `context_nonconforming`, `context_dirty`, `context_conflicted`, `conflict_pending`, `history_unresolved`, `primary_missing` (no tracking primary; the local primary is optional in this mode), a merge, rebase or cherry-pick in progress at the root (`primary_conflicted`, as Cycle 03's branch close maps it, `closure/observe.rs` about 1037-1041), and an unfinished promotion record of the document (`recovery_required`, naming its request: the binding's hold, `bind/lifecycle.rs` about 396-435, the CLI contract's decision 33). Dropped, because nothing touches the primary (R-6): `primary_not_checked_out`, `primary_dirty`, `primary_ahead_of_remote`, `context_behind_remote`, `integration_conflict`, `document_invalid_after_integration`, and the binding's `identity_required` with the runner's `require_identity`. `history_unknown` does not block (decision 10, R-5): the context child's fetch settles the history. Another unfinished synchronization of the branch is not a prepare blocker: the child answers `busy` at confirm (R-18).

**The digest (R-7)** binds the domain, the item, the document's path, the branch, the primary branch, the remote, `L`, `R`'s relation to `L` (absent, equal or behind is one state, since a push of `L` moves `R` to it; `R` itself is bound when it is ahead of or beside `L`), the situation (`first` or `again`) and the `pull_request` object the preview shows. It does not bind the tracking or local primary, which move. So a poll that first creates `R` at this clone's own push changes nothing, while a save, another clone's publication fetched, a link given, or for `first` a change of forge setting or remote URL (for `again` the previewed link is the row's) between prepare and confirm is `external_change` at confirm. A merge fetched between prepare and confirm leaves the digest as it was; confirm's re-observation finds the primary holding the document, and the binding answers `already_applied` as prepare would (Part G item 15, C19).

**The preview's details** are a new `PreviewDetailsDto` variant, `PullRequestPromotionPreviewDto`, tagged `"type": "pull_request_promotion_preview"`, holding the item, its path, the branch, the primary, the remote, `L`, `R`, the situation and the `pull_request` object: the link row's for `again`, the one that would be built now for `first`.

## Part C: Confirm

1. **At the boundary.** The CLI compares the confirm's re-observation with the consent before anything is accepted (Baseline Fact 25): a difference answers `external_change` and records nothing; a document the primary now holds answers `already_applied` as prepare does, with no record (Part G item 15). In the library, where the runner's revalidation sees the same, a difference is a refused record and a held document answers `already_applied` with no record.
2. `begin_record` with `integration_mode` `pull_request` and the columns of Part A.
3. **Every later call of the same request** obeys the re-run table RR below (decision 14), before and around its child.
4. The context child, under `child()`, in `promote_branch`; it always runs in pull-request mode (`runs_context_child` true, R-19). It synchronizes the branch with its remote copy and the remote's primary and publishes it, as `item sync` does (Baseline Fact 13). On completion, step `context_synchronized`.
   - A child that stopped answers as `item sync` answers that stop (the same code and data, Cycle 03 R-5), and the record stays `confirmed` for the same request (RR1).
   - A child that ended is let go, and `end_branch` answers by the second table below.
5. **After a child that completed** (RR2), `branch_step`, under the lease and with no network, answers by the first table below, reading the child's category through `child_state`, and finishes the record in one transaction that stores `answer_code` and the category and, where the table says, writes the link row (kind `document`, `given_at` from the request's clock), only while the document's context exists (RR8). It returns `Finished`: a pull-request promotion has no publication child and never reaches `finish_branch` (R-1). `RunEvent::Recording` is not emitted for a promotion (Part G item 11).

While a pull-request promotion record is unfinished, every retirement path skips or refuses its document (decision 13, table F below).

R-3 is judged, in both tables, with the tracking primary as it is when the record answers, which the child's fetch has moved (R-12): on the child's authority OID after a child that completed, and on the consented tip after one that ended.

**After a child that completed**, the first row that matches:

| Situation | Answer | Record | Link row |
| --- | --- | --- | --- |
| R-3 holds | `already_applied`, `primary_holds` true, no link | `complete`, `primary_holds` | untouched |
| the record's situation is `again` | `already_applied`, the row's link | `complete`, `already_promoted` | `given_at` renewed (an update of `given_at` alone) |
| otherwise | `ok`, the link built now | `complete`, `promoted` | written |

**After a child that ended** (the record at `confirmed`), the first row that matches:

| Situation | Answer | Record | Link row |
| --- | --- | --- | --- |
| R-3 holds (with `R` read as absent after `remote_branch_deleted`) | `already_applied`, `primary_holds` true, no link | `abandoned`, `primary_holds` | untouched |
| `remote_branch_deleted` | `remote_branch_deleted`, way out `item republish`, then a new promote (decision 11) | `abandoned`, `remote_branch_deleted` | deleted, so the new promote after the republish is `first` |
| `history_unresolved` | `recovery_required`, blocker `history_unresolved`, way out `item resolve-history`, as `item sync` answers it | `abandoned`, `history_unresolved` | untouched |
| the branch gone | as Cycle 03 answers `ContextGone` | `abandoned`, `context_gone` | untouched |

The link of `first` is built once, when the record finishes, from the record's remote's URL as `git2` reports it, the forge setting, the branch and the record's `primary_branch`, through `forge::recognise` and `forge::pull_request_link` (Cycle 03 R-25), and stored; `again` returns the stored link (R-17). A missing URL, or a configuration that cannot be read, never fails the promote: the link then has a null URL. A same-request re-entry of a finished record answers from `answer_code`; a replay answers with its stored envelope, and only a replay whose envelope was lost (C15) rebuilds the answer from `answer_code` with the row's link as it is then.

## Part D: The Data, The Preview And The Contract

**The data (R-8).** A new `MutationDataDto` variant, `PullRequestPromotionMutationDto`, tagged `"type": "pull_request_promotion"`, with `item_id`, `publication` (`published` or `current`, from the child's category; null when no child completed), `primary_holds` (boolean) and `pull_request` (the object, or null). It is the data of every finished answer of a pull-request promotion: `ok`, `already_applied`, and the ended answers `remote_branch_deleted`, `recovery_required` (`history_unresolved`) and Cycle 03's `ContextGone` answer. A child that stopped carries the synchronization's own data. Its schema is `schemas/v1/pull_request_promotion_mutation.schema.json`, a `DATA_ROOTS` entry.

**The preview.** `PullRequestPromotionPreviewDto` (Part B), schema `schemas/v1/pull_request_promotion_preview.schema.json`, a `DATA_ROOTS` entry as `lifecycle_preview.schema.json` is. Its blocked prepares answer with the existing `lifecycle_blocked` shape.

**A prepare's `already_applied`** carries no data (R-4): in a pull-request repository it means the primary holds the document. It uses the prepare shape Cycle 03's withdraw adds (Baseline Fact 14).

**`from_stored` (R-25).** A tag-guarded arm reads the new data for `document promote` before the `DocumentPromote | TicketClose` lifecycle arm, which is guarded on the lifecycle shape (as Cycle 03 guards it for `TicketClose`); and `document promote` joins the synchronization-conflict arm and, last, the host-data arm, as Cycle 03 adds its verbs to them, so a stored stopped promote keeps its data.

**The way out (decision 11, R-22).** `way_out.rs` gives a `remote_branch_deleted` that carries the new data the way out `item republish` of its `item_id`, then a new `document promote --prepare` (not the same request: the record is finished). It is keyed on the data, so the direct promote's, the close's and `item sync`'s way outs do not change. The CLI contract's answers table gains a `document promote` (pull-request) row for `remote_branch_deleted`, with its recovery action `item.republish` (the action the finished answer offers), its `next:` lines and the golden `document_promote_pull_request_remote_branch_deleted` (D-1, E-10); `recovery_required` with `history_unresolved` uses the existing `document promote` row for that blocker, and Task 9 names a `recovery_tables.rs` edit if its recovery differs.

**No new result code, blocker, verb or operation action.** A pull-request promotion is a `document_promotions` row, listed by `operation list` as a `promote` with its step.

**Goldens (R-23).** One per output contract: `mutation_v1` `document_promote_pull_request_ok` and `document_promote_pull_request_remote_branch_deleted` (over SSH); `cli_v1` `document_promote_pull_request_preview` (JSON and text), `document_promote_pull_request_primary_holds` (the prepare's `already_applied`, JSON and text) and `document_promote_pull_request_blocked` (JSON and text). `item sync`'s link for a document uses Cycle 03's `pull_request_link` data and golden.

**Human output.** The preview prints its effects and the link's `human_line()`. The answer prints `publication: <state>` when a child completed, then the link's `human_line()` on its own line, or the fixed sentence `the primary branch already holds this document` when `primary_holds` is true; a prepare's `already_applied` in a pull-request repository prints the same sentence. A unit test in `src/bin/manyhands-cli/lifecycle_tests.rs` pins the three lines.

**The desktop.** Compile-level arms for the new preview and data (R-14). "Approve and merge" keeps its words until Cycle 06.

## Part E: Reads: The Document's Link

`fill_complete_read` fills `pull_request` for a document as well as a ticket (decisions 3 and 9, R-9): for a document read from its active context, with a link row, the row's link while the primary does not hold the document, and null once it does. It is null for a document with no row or no active context, and in every list, as today. It reads the row in either mode, as the ticket's does.

Show's check is the cheaper twin of R-3 (decision 9), `document_link_outstanding`, built on `proof.rs`'s entries-only `unheld_entries`: the document is held when a primary R-3 may use holds a regular file at the document's path in `L`, `unheld_entries(L, primary)` is empty, and `R` stands as R-3 requires. It loads no blobs and scans no other item. It differs from R-3 only in a repository with missing objects, a document ID held at two paths, a primary copy that does not parse, or a document moved on the primary (K-11). Promote and `item sync` keep the full proof.

`ItemDto.pull_request`'s documentation and `item.schema.json`'s description change to match (D-1). `ClosureDto.publication` is unchanged.

## Part F: `item sync`'s Link For A Document

Cycle 03's rule for a closing ticket (its Part H, decision 12) gains documents (decision 4, R-10): when `item sync` of a document context in a pull-request repository publishes, or finds current, the branch, and the document has a link row, and the primary does not hold the document after the synchronization (R-3, the full proof), the answer carries Cycle 03's `pull_request_link` data with the row's link. `item sync` never writes a document's row, so `given_at` is not renewed. Every other `item sync` answer is unchanged, in a direct repository too.

## Part G: The Lifecycle's Adaptations

These are required. The design checkpoints of Tasks 1 to 4 write each one down against the source before code:

1. `PromotionRecord::path()` and `answered()` read `integration_mode` and `answer_code`; `begin_record` takes the mode and Part A's columns from the observation.
2. `DocumentPromotionLifecycle`'s `branch_step` (the first table, under the lease, finishing the record, returning `Finished`) and `end_branch` (the second table) are implemented; `begin_publication` and `branch_answer` stay unreachable for a promotion (it has no publication child), and `BranchFinish` stays `Infallible`.
3. Promotion's `type Outcome` becomes an enum of a direct and a branch outcome, as the closure's `ClosureOutcome` is; `DocumentPromotionResult` gains `Branch(BranchPromotionOutcome)` and its index-pending twin; `branch_outcome` reads the record's `publication_category` and `answer_code`; the exhaustive matches of Baseline Fact 7 gain arms.
4. The binding's `Called::Branch` holds either lifecycle's branch outcome, `Promote` builds it, and a promotion twin of `branch_code` maps `PromotionAnswer` to its code; the binding reads the link row to build the answer's `pull_request`; `reached_*` and the recorded effects read the path; the CLI's retry guard reads the new data.
5. The digest's domain constant sits beside `manyhands promotion v1`.
6. The mechanism that gives the RR table, through a defaulted `Lifecycle` hook the closure does not take, so the closure's runner behaviour is unchanged (Task 4's checkpoint, U-3).
7. The places that read a record's second slot (`remote_identity_of`, `children_contexts`, `audit`) answer for a promotion branch record with an empty second slot.
8. A pull-request promotion takes no new hold beyond item 14. While it is unfinished it holds what an unfinished promotion holds today (Baseline Fact 23): its document's prepare, its context child's reservation while that child stands, a change of the repository's setting made in this clone, and `context sync-local` of every item (K-5).
9. The link helper is shared: Cycle 03's `give_link` and `branch_link` take the kind (or a document twin sits beside them), so the document's row is written with kind `document`; renewing `given_at` is an update of that column alone.
10. In pull-request mode `runs_context_child` is true and `require_identity` passes.
11. `RunEvent::Recording` is not emitted before a promotion's `branch_step`.
12. Promotion's `type Preview` becomes an observation type that carries the mode and the pull-request facts (`L`, `R`, the situation, the link, the endpoint), with the primary OID optional or absent in pull-request mode, so that `Ready`, the digest and `begin_record` take it; the checkpoint chooses the shape that changes the fewest of `DocumentPromotionPreflight`'s exhaustive matches, and lists each match it changes (E-12).

## Rulings

Each: decision — why — cost if wrong.

- **R-1** The pull-request promote is a branch record of `document_promotions` with one child, and `branch_step` or `end_branch` finishes it — decision 1, and nothing of Manyhands' own is written on the branch, so there is no closure-writing hook and no publication child — `finish_branch` and the publication slot are dead code for a promotion.
- **R-2** A record's mode is fixed when it begins; prepare chooses the observation by the configuration, and the pull-request observation's digest has its own domain — Cycle 01 decision 11, Cycle 03 R-2 — a switch between prepare and confirm costs a re-prepare.
- **R-3** "The primary holds the document" is the proof for the tip against the tracking primary, or against the local primary when it is the tracking primary or behind it, with `R` absent, equal or behind (and absent after `remote_branch_deleted`) — the RFC's content proof; in this mode the local primary only ever fast-forwards to the tracking primary, so a local primary ahead holds work no one else has; `R` ahead or beside is work the clone has not merged — a document whose remote copy has another clone's later saves reads not held until a synchronization merges them.
- **R-4** When the primary holds the document, prepare answers `already_applied` with no data and no record, as Cycle 03's withdraw prepare does — there is nothing to publish, cleanup belongs to retirement, and in a pull-request repository that code at prepare has one meaning — a caller learns the reason from the code and `document show`, not from data.
- **R-5** Decision 10's mechanics: the pull-request observation reads `Unknown` history as no blocker, and the context child's fetch settles it (Baseline Fact 4) — a branch deleted since is found at confirm (`remote_branch_deleted`), not at prepare.
- **R-6** The pull-request prepare drops the root blockers except a merge, rebase or cherry-pick in progress at the root, drops the integration blockers, `identity_required` and `require_identity`, and keeps `primary_missing` for a missing tracking primary; the local primary is optional — nothing touches the primary, and the child's own stops (identity included, for a merge of the primary into the branch) answer as `item sync`'s — a root that is dirty or on another branch does not stop a promote.
- **R-7** The digest binds `L`, `R`'s relation to `L` (absent, equal or behind is one state), the situation and the previewed link — the consent is to publish what was previewed and to give the link it showed — a save, or for `first` a change of forge setting, between prepare and confirm costs a re-prepare.
- **R-8** A new data type and preview type for the pull-request promote — Cycle 03 decision 3 (the close's data type is the close's own) — two schemas more.
- **R-9** `document show` fills `pull_request` for a document from its active context while the primary does not hold it, in either mode, by the cheap check — decisions 3 and 9 — show disagrees with promote only in K-11's cases.
- **R-10** `item sync` reads a document's row and never writes it — decision 4 (it never creates a link) — `given_at` is renewed only by promote.
- **R-11** `primary_holds` finishes the record without touching the link row, which retirement deletes; a `remote_branch_deleted` end deletes it — decision 3 (the link ends by the proof), and the RFC's "or abandoned" for a declined pull request — a stale row outlives a merge until retirement, hidden by reads; K-9 is its edge.
- **R-12** R-3 is judged with the tracking primary as it is when the record answers, which the child's fetch moved: on the child's authority OID after a child that completed, on the consented tip after one that ended, before every other row — an ended child records no tracking primary (Baseline Fact 24), and a forge merge during the promote must report the document held — a poll that moved the tracking primary further since the child only makes the judgement fresher.
- **R-13** A child that ended abandons the record with the refusal `reconfirmation_required` and its answer, as Cycle 03's `abandon_branch_record` does — the record's CHECK ties `abandoned` to a refusal — an abandoned row can carry a success answer (`primary_holds`), as Cycle 03's `already_closing` does.
- **R-14** The desktop gets compile-level arms only — Cycle 06 owns its design — the desktop shows a generic preview and no link actions until then.
- **R-15** No new SSH case: Cycle 03's case gains the promote steps — AGENTS.md's Testing Strategy, decision 6 — that case runs a few seconds longer, and fails for either Cycle's regression.
- **R-16** The runner takes its clock from the request (Cycle 03's `LifecycleRequest.clock`) for `given_at` — AGENTS.md's no real waits — none.
- **R-17** The link is built once, at `first`, and `again` returns the row's link and renews `given_at` alone — decision 2 (the same link) — after a change of forge setting or remote between records the old link is offered until the row ends (K-13).
- **R-18** Another synchronization of the branch is the child's `busy` at confirm, not a prepare blocker — the direct promote has no such blocker, and the closure's queries tickets only — the person learns of it at confirm.
- **R-19** In pull-request mode the context child always runs, even when the plan would have been `AlreadyContained` — it is what publishes — none: a held document answers at prepare.
- **R-20** Decision 14's rules are the RR table's required outcomes, given through a defaulted hook the closure does not take — a stopped promote must never wait for good, never publish what was not previewed, and never be refused for its child's own moves — a person who saves during a stopped promote re-prepares it.
- **R-21** Decision 13's rules are the F table's required outcomes: every retirement path skips or refuses a document whose pull-request promotion is unfinished, as it does a ticket whose closure is unfinished — a re-run's child needs the context, and a retired one answers `TargetNotMaterialized` for good (Baseline Fact 21) — a merged document whose promote is stopped is retired only after its request runs again.
- **R-22** The way out of a pull-request promote's `remote_branch_deleted` is `item republish`, then a new promote, keyed on the new data — decision 11 — the direct promote, the close and `item sync` keep theirs; after a squash on which the primary moved on, the republish revives a merged branch (K-12).
- **R-23** One golden per output contract, and `item sync`'s document link reuses Cycle 03's golden — AGENTS.md's golden rule — the human lines are pinned by a unit test instead of text goldens for every answer.
- **R-24** The preview always lists `context_synchronized`, `context_published` and `pull_request_link` — the RFC's list, and the synchronization may merge the primary in and publish even when `L` equals `R` — a preview can promise a publication that turns out current.
- **R-25** `document promote` joins `from_stored`'s synchronization-conflict and host-data arms — a stopped promote answers with the synchronization's data, and a replay must keep it — none.
- **R-26** After its child completed, a pull-request promotion checks neither its remote nor a cancellation before `branch_step` — the rest is local and needs no network, so finishing loses nothing — a `request cancel` that lands then is not honoured.
- **R-27** The record stores its situation, primary branch and endpoint digest at begin, besides its consented tip — a re-entry has no observation, and a record whose child completed must finish without the live configuration — four immutable columns more.
- **R-28** The re-run rules of decision 14 and the fence of decision 13 are required outcomes (tables RR and F), and their mechanism is Task 4's checkpoint's — three review rounds found blockers in each prose mechanism — the mechanism is reviewed at the checkpoint and in Task 4's review, not in planning.
- **R-29** At confirm the CLI's boundary refuses a consent difference with nothing recorded, and the binding answers a held document `already_applied` before it — Baseline Fact 25 — C18 and C19 write a refused record only in the library.

## Alternatives Rejected

- Handing the promote to `item sync`'s binding with no lifecycle record: decision 1; a stopped promote would be listed, resumed and replayed as an `item sync`, the separate-runner shape Cycle 03 left after three review rounds.
- Answering `already_applied` at prepare with no synchronization while the link is outstanding: decision 2; the pull request would lag the person's saves.
- A link that ends only when its row is deleted: decision 3; `document show` would offer a merged pull request's link.
- The full proof in `document show`: decision 9; it reads every blob of two trees on every show.
- Keeping `history_unknown` as a prepare blocker: decision 10; the usual path, `item sync` and then promote, would need a poll first.
- Recording the consented tip and ending a retired record through `ContextGone` instead of a retirement fence: decision 13; a garbage-collected tip would answer `context_gone` rather than "already applied".
- Leaving a stopped promote to Cycle 03's `interrupted` rule: decision 14; a promotion records no base, so it would wait for good.
- A blocker `already_promoted`, or data on a prepare's `already_applied`: there is nothing to do, which is `already_applied`, and Cycle 03's withdraw prepare already gives that answer with no data.
- Rebuilding the link on `again`: decision 2's "the same link".
- Previewing `context_published` only when `L` differs from `R`: the RFC lists it, and the synchronization can publish a merge of the primary.
- A new SSH case: decision 6.
