# Wave 06 Cycle 03 Design: Ticket Close In Pull-Request Mode, The Closing State And Withdraw

Cycle document: [Wave 06 Cycle 03](../Cycles/wave-06-cycle-03-pull-request-close.md). Ticket: vh-gy8gz (`01M87683QK8E34EYY8KS4VQG9Y`). Authority: the [Pull-Request Mode RFC](../RFC/pull-request-mode.md) and the Cycle document's Product-Owner Decisions.

## Intent And Approval Boundary

In a pull-request repository, make `ticket close` record the closure on the ticket's branch, publish the branch and give the pull request link, never committing to or pushing the primary. Show a closure the primary does not hold yet as `closing`, keep its dependents blocked, let it be withdrawn, let two clones' closures settle themselves, and close a ticket whose branch merged first (with its remote branch gone) or that has no branch, through a new branch holding only the closure. All three are modes of the existing ticket-closure lifecycle (decision 13). Approving this design approves the Cycle document's Required Contract and the rulings below. It does not authorize implementation, pushes other than the ticket branch, or merging.

## Conventions

- Names are cited as `file` and `function`. Line numbers are approximate, at `d88896b8`; Task 0 re-checks every one.
- "Pull-request repository" means a valid configuration with `integration = "pull_request"` (Wave 06 Cycle 01).
- "The tracking primary" is `refs/remotes/<publication remote>/<primary>`, as last fetched. "The local primary" is `refs/heads/<primary>`.
- "The primary's copy" of a ticket in a read is the row the index stores for it in a context that is not an active item context (rank `PRIMARY_COPY` in `row_rank`): normally the root checkout's working tree (K-9).
- "A provisional closure" is a closure (`closed_at` and `closed_by`) that the ticket's branch holds and the relevant primary does not (RFC, Provisional closure). Two closures are "the same" when both fields are equal.
- "The lifecycle" is the existing ticket-closure lifecycle: `promotion/run.rs` (`run_lifecycle`, `promote_inner`, `finish_steps`, `child()`), `closure/` and the `ticket_closures` record. "A branch record" is a `ticket_closures` row whose path does not integrate (Part D): a pull-request close, a withdraw or a new branch. "A direct record" is today's.
- "Stops" means a step ended without the lifecycle's operation ending: the request record stays accepted, the closure record stays unfinished, and the same request continues it, as for a direct close.

## Part A: The Closing State

**The values.** `ClosureState` gains `Closing => "closing"`, after `Closed`. `DependencyState` gains `Closing => "closing"`, after `Unresolved`; `parent.state` shares it. `ReadinessReasonCode` gains `ClosingDependency => "closing_dependency"`, after `DependencyCycle` (R-8). The schema enums list the values in that order (`item.schema.json` `closure.state`, `parent.state`; `dependency.schema.json`; `dependency_tree_node.schema.json`; `readiness_reason.schema.json`), and the documentation that names the two states is updated (`ClosureDto`, `ReadinessState`, `DependencyDto`, `ReadinessDto`, `items.rs` about 42, `graph.rs` about 56 and 293, `item.schema.json` about 99). `ClosureDto` gains `publication` (Part C).

**The derivation (R-6, R-7).** For each ticket a read computes one fact from the stored rows it holds, after `graph.rs`'s moved-context substitution: the closure (both fields) of its primary's copy (rank `PRIMARY_COPY`), or none. Then, with "the copy read" being the effective copy (lists, `show`) or the file `show --path` read:

| The copy read | Primary's copy | State | `closed_at`, `closed_by` shown |
| --- | --- | --- | --- |
| no `closed_at` | holds a closure | `closed` | the primary's copy's |
| no `closed_at` | open, or absent | `open` | none |
| holds a closure, and is the primary's copy | — | `closed` | its own |
| holds a closure (an active context's copy) | holds a closure | `closed` | the primary's copy's |
| holds a closure | open, or absent | `closing` | its own |

So `ClosureDto`'s rule holds: the fields are set exactly when the state is `closed` or `closing`. The fact is passed, per ID, wherever the state is needed: `closure()` for lists, `show` and `show --path`; `Targets::of`, `Targets::stored_node` and `Related::of`; `TicketFilter::matches`; and `TicketGraph`, for readiness, tree lines and the deps root. The derivation does not read the mode (decision 11).

**Readiness (decision 9).** `TicketNode` keeps `closed`, now true only for `closed`, and gains `closing`. Every readiness decision reads `closed`, so a closing ticket counts as open for its dependents: an edge to a closing ticket gives `closing_dependency` in place of `open_dependency`, and tree lines and the deps root report `closing`. The queries leave closing tickets themselves out: `ticket ready`, `ticket blocked` and `ticket list --ready`/`--blocked` never list a closing ticket; `ticket plan` computes its batches with closing tickets as open nodes, then removes closing tickets from its batches and from `unplannable`, and drops empty batches, as a filter does: each batch keeps its number in the plan of every ticket (R-9, decision 15); `ticket critical-path` gives closing tickets no length and leaves them out of its chain. A closing ticket's own `readiness` field is computed as an open ticket's. `tickets_made_ready` is unchanged.

**The filter.** `ClosureFilter` gains `Closing`. `Open` matches `open` and `closing`; `Closing` only `closing`; `Closed` only `closed`. The CLI's value parser takes `open|closed|closing|all`, `dispatch.rs` maps `closing` explicitly, and the help text says so.

**Human output.** `item_line`, `item_show` and `dependency_line` print the state's `as_str()`. `item_show` adds `Publication: pending` or `Publication: published` when `closure.publication` is set, and the link's `human_line()` when the item has one.

**The desktop (R-22).** Compile-level arms only: `ClosureState::Closing` maps to `Lifecycle::Open`, `DependencyState::Closing` as `Open`, `ClosingDependency` as `OpenDependency`, and `ClosureFilter::Closing` gets an arm the desktop never selects.

## Part B: The Guards, The Save Check And Immutability

**The domain guard (R-10).** `require_ticket_open` gains the repository's integration: in a pull-request repository it reads only the local primary's tip; in direct mode it reads both tips, as today. `refuse_closed_ticket`, `bind/republish.rs` and `bind/resolve_history.rs` pass the mode of the configuration they hold; `context_release.rs` passes `Direct`. So in a pull-request repository a closing ticket accepts `ticket save`, slug assignment, context prepare, `comment add`, `item republish` and `item resolve-history`, and a ticket whose local primary holds a closure refuses them with `ticket_closed`. Commits made with Git in the ticket's worktree are not Manyhands writes and meet no guard (RFC). While a branch record is unfinished these writes are held (Part D's hold).

**The binding precheck.** `refuse_closed` keeps comparing with `ClosureState::Closed`, so it lets a closing ticket through, and the domain guard decides. The other `== ClosureState::Closed` checks keep their comparison: drafts and the desktop's edit action treat a closing ticket as open, and the desktop's "Close ticket" stays offered, answering `already_closing` (R-22).

**The save check (R-11).** A ticket save, in both modes, refuses with `invalid_input` when the resulting file's `closed_at` or `closed_by` differ from the ticket at the context branch's head (or from an open ticket, for a context with no ticket yet). It runs in the domain save under the lease, before the checkpoint.

**Immutability in a ticket context (R-12).** `validates_resolution_sides` and `validates_external_integration` gain an optional primary-side commit and check the ticket's closure across all three sides at once. When no primary side is given, the rule is today's (each side's closure must be kept). When one is given, the result's closure must be:

- the primary side's closure, when the primary side holds one;
- otherwise none, the local side's closure or the incoming side's closure (not the base's alone).

`preserves_item_invariants` keeps its other checks, and its per-side closure check applies only when no primary side is given. The primary side is given only in a remote synchronization of a ticket context with a pinned window: in its Context stage it is the window's `primary_oid`, and in its Primary stage the step's incoming commit (the same fetched primary). A primary-target synchronization, a local synchronization and window 0 give none. `remote/conflict_read.rs` reads the window's `primary_oid` from the `Recorded` step's window number. `classify_conflict_entry` is unchanged, so a conflict holding two different closures stays external repair only.

**The primary's closure in a ticket context (R-30).** A remote synchronization of a ticket context does not publish a head whose ticket lacks a closure that the primary it fetched holds: a merge it prepares (clean) is given that closure's fields, canonically, before it is committed (in `integration/prepare.rs`, with Part G); and in the push decision, reached from both the merging path and the plan path, a head whose ticket does not hold the fetched primary's closure (`evidence.primary_tracking_oid`) is not pushed: the synchronization answers `ticket_closed`. An `item sync` so refused ends its operation (as `HistoryUnresolved` does); a lifecycle child so refused is kept for its parent, which lets it go. A forge merge after the fetch is not seen until the next fetch.

## Part C: The Link Record, The Pull Request Object And The Item's Fields

**The object (decision 5).** `pull_request: { source, target, forge, url }`: `source` the ticket's branch, `target` the configured primary, `forge` a forge kind (`bitbucket-cloud`, `bitbucket-data-center`, `github`, `gitlab`) or null, `url` a string or null. Its schema is `schemas/v1/pull_request.schema.json` and its DTO `PullRequestDto`, both Cycle 02's (vh-c97se). Task 0 checks `origin/main`: if they are there this Cycle uses them; if not, this Cycle adds them in exactly that shape and under those names, and whichever Cycle lands second merges (R-26). `forge` is a schema enum registered in `contract_enumerations`.

**Building it (R-25).** From the publication remote's URL as `git2` reports it, the configuration's `forge()`, the branch `manyhands/ticket/<ULID>` and the primary, through `forge::recognise` and `forge::pull_request_link`. A missing URL never fails a step.

**The record (R-14).** A registry table, keyed per item, holding what this clone gave:

```sql
CREATE TABLE pull_request_links (
    repository_id INTEGER NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
    kind TEXT NOT NULL CHECK(kind IN ('ticket','document')),
    item_ulid TEXT NOT NULL,
    source TEXT NOT NULL,
    target TEXT NOT NULL,
    forge TEXT,
    url TEXT,
    given_at INTEGER NOT NULL,
    PRIMARY KEY(repository_id, kind, item_ulid)

```

A branch record's completion that gives a link, and every `item sync` answer that carries one (Part H), upserts its row, the record's in its completing transaction. One helper deletes an item's row, and both retirement paths call it in their finishing transaction: `cleanup.rs` `retire_context` (the direct close's and promote's cleanup, and Part F) and `context_retirement/record.rs` `finalize_index`'s retiring branch (a poll's retirement, `context retire` and the refresh path; its preserving branch keeps the context and the row). A withdraw keeps it. The table is created by a named, additive migration, marker `wave_06_pull_request_links_v1`, run after `migrate_pull_request_mode`, adding its table by checking the schema, in an immediate transaction with a read-only precheck.

**On the item (R-15).** `ItemDto` gains `pull_request`, after `readiness`: the record's link in `ticket show` and `ticket show --path` for a ticket that has one; null in every list, for a document (Cycle 04 fills documents), and for a ticket without a record. `ClosureDto` gains `publication`, filled by `show` and `show --path` for a closing ticket in a pull-request repository: `published` when the ticket at the remote tracking ref of `manyhands/ticket/<ULID>` holds the same closure, `pending` otherwise (including with no tracking ref); null for any other state, in direct mode (where a branch-only closure is never published), and in every list (RFC: "shows in `ticket show` as closing, with publication pending"). Both fields are required in `item.schema.json`, and null in a list means "not read here".

## Part D: The Pull-Request Close As A Mode Of The Lifecycle (Decision 13)

**The record (R-1).** `ticket_closures` is rebuilt once (a named migration, marker `wave_06_closure_modes_v1`, by rename and copy with an explicit column list, after `closure_refusal_blockers_v2`) and gains:

| Column | Meaning |
| --- | --- |
| `integration_mode` | `direct` or `pull_request`: the mode the record began in, fixed for its life (Cycle 01 decision 11) |
| `action` | `close`, `withdraw` or `new_branch`, fixed for its life |
| `withdraw_oid` | a withdraw's commit, written before its ref moves |
| `retired_oid` | a new branch's old context tip `T` |
| `pending_ref` | a new branch's commit is held by `refs/manyhands/closures/<operation ULID>` until its branch exists; deleted by every abandon and by step 3 |
| `answer_code` | a finished branch record's answer (its code, the closure's recording and the publication), written in the transaction that finishes it, abandon included; a same-request re-entry and a replay answer from it |

Existing rows read `direct` and `close`. A record whose `integration_mode` is `direct` and whose `action` is `close` is a direct record, unchanged in every rule. Every other record is a branch record: it never integrates and never cleans up. A withdraw is a branch record in either mode (decision 11); `new_branch` and a `close` in `pull_request` mode exist only in a pull-request repository. The CHECKs that tie `closing` to a record closure are restated per action: a `close` record at `closing` holds `closed_at` and `closure_oid` (kind `record`), or neither (kind `existing`); a `new_branch` record holds `closed_at` and `closure_oid` from step 1, with kind `record` or, for a kept closure, `existing`; a `withdraw` at `closing` holds `withdraw_oid` and kind `existing`. A branch record's `base_oid` is the tracking primary its hook read. The rebuild leaves the `closure_refusal_blockers_v2` rebuild's own DDL frozen at its version, and inserts the new marker on the path that creates the table. The unique unfinished index keeps one unfinished record per ticket, of any action. The record never holds `closed_by`, a title, a body or a URL.

**Steps (R-2).** A branch record uses existing step names, with `ClosureStep::permits` and `validate` extended by its action:

| Action | Steps |
| --- | --- |
| `close` (pull-request mode), `withdraw` | `confirmed` → `context_synchronized` → `closing` (the commit written and the context moved) → `published` or `publication_pending` → `complete` |
| `new_branch` with an old context or published history | `confirmed` → `worktree_removing` → `worktree_removed` → `branch_deleted` → `closing` (the retirement done, the commit on `P`, the branch and worktree made) → `published` or `publication_pending` → `complete` |
| `new_branch` otherwise | `confirmed` → `closing` → `published` or `publication_pending` → `complete` |

`new_branch` gains the step `retired` (the retirement's transaction committed) between `branch_deleted` and `closing`. `abandoned` is reachable from `confirmed`, `context_synchronized` and, for `new_branch`, `retired` before its branch exists (as today, plus that one). A branch record completes through a new completion function that requires no retired context and stores `answer_code`; it uses the existing publication categories, and its outcome is in `answer_code`, so `PublicationCategory`, which `document_promotions` shares, is unchanged. `supersedable()` is false for every branch record, whatever its cleanup category.

**The children (R-3).** A branch record's first child is the existing `Context` child (from `confirmed`). Its second child slot (`primary_attempt`, `primary_sync_id`) holds the publication child: a new `ChildRole::Publication`, a synchronization of the ticket's context target, allowed from `closing` and `publication_pending` of a branch record (`ParentFacts` carries the closure step and the path for `child_allowed`). The publication child's first attempt is minted in the transaction that moves the record to `publication_pending`; from then on (`primary_attempt > 0`) every call of the record goes straight to the publication child, and never runs the hook, its reconciliation or step 3's checks again. Every completion after a stopped child lets the child go first, so no stopped child outlives its record. `validate_request`, `synchronization_target`, `remote_identity_of`, `children_contexts`, `primary_authority` and `remember_publication` read the record's path for the second slot. Everything else about children is `child()`'s, unchanged: attempts, replay, restart, cancel and acknowledge, replacement, and letting a child with nothing to lose go. Because the slot keeps its columns, every list of Baseline Fact 12 covers the publication child without change; the conflict verbs' two lookups (Baseline Fact 10) gain the second slot for a branch record.

**The runner (R-1).** `promote_inner` and `finish_steps` read the record's path. For a branch record: after the context child, the closure hook runs under the lease without an integration (step `closing`); then `finish_steps` runs the publication child in place of the primary child, and completes with no cleanup. For `new_branch`, step 1 and the retirement run before the hook. The outcome types gain the branch shape: `TicketClosureOutcome`'s integration and cleanup become optional (absent for a branch record), and the binding's `reached_*`, `parent_integrated`, `parent_effects` and `made_ready` read the path. The branch hook is built from the direct hook's parts (R-34): the lease, `context_synchronization_unfinished` false (busy otherwise, naming the blocker), the identity against the consented `closed_by`, `closed_at` frozen in the record before the commit (C6), a checkpoint-only commit builder (no merge into the base), a `begin_closing` variant per action, `move_context_to_checkpoint_with`, and a reconciliation generalized to the record's written commit (`closure_oid` or `withdraw_oid`: nothing written, checkout done, or the tip is that commit or a descendant holding its closure state). The direct hook's base checks (`primary_advanced`, "the context holds the base"), `current_base`, `post_checkpoint_result` and `adopt_written_closure` do not apply to a branch record. `finish_steps` returns a branch record's publication child's error to the binding, as the context child's is returned, rather than folding it into a publication category.

**The hold (R-17).** `written_closure_unfinished` covers a branch record from `closing`, and a `new_branch` record from step 1 (once `closure_oid` is stored), until it finishes. While it holds:

- `closure_holds_context` answers `Busy` to every reservation and restart of the ticket's context target, except a validated `ChildExecution` of the holding record's own publication child;
- the poll does not materialize, fast-forward or retire the ticket's context (as today; the poll's retirement gains the check);
- for a branch record, `refuse_closed_ticket` (save, slug, context prepare, the comment checkpoint), `bind/republish.rs`, `ticket repair`, `context retire` and the ticket's own `context sync-local` answer `recovery_required` naming the record's request; for a direct record the existing answers stay (the guard's `ticket_closed`, and `admit`'s rules);
- `item resolve-history` passes a branch record's hold (ruling 19, which the owner may overturn): it changes the history record and not the context, and the record's same request then continues, so a publication child stopped by unresolved history can be cleared; otherwise the record would hold the ticket for good (`bind/resolve_history.rs` takes no hold of a branch record; `item_resolve_history_passes_a_branch_record_s_hold`);
- `context release` refuses, as today for a context an unfinished closure owns.

Before `closing`, a branch record holds what a direct one holds: its prepare is held for a new request, and its step 3 waits for any other synchronization of the context (`context_synchronization_unfinished`, busy). `context sync-local` in the repository answers as today while any closure record is unfinished (K-10).

**Consent and dispatch (R-2).** Prepare reads the configuration. In a pull-request repository, and for every withdraw, the observation is the branch record's and its digest's domain is `manyhands pull request closure v1`, which binds the action and everything listed below; otherwise it is today's direct observation, domain `manyhands closure v1`. Confirm re-observes as today, so a prepare made in one mode is `external_change` when confirmed in the other, with nothing written. A same-request retry finds its record and continues it in the record's mode and action.

**Prepare** reads local state only, with no network, lease or write. For `ticket close` in a pull-request repository, the ticket's situation is decided in this order:

1. the local or the tracking primary's ticket holds a closure: blocked `ticket_closed` (blocker `already_closed`);
2. a context exists and its remote branch's deletion is evidenced, by a fetch's record (`DeletionEvidence::Fetched` of `republish_evidence`) or by the close's own push finding: `new_branch`, keeping a provisional closure the context's ticket holds (R-21). The push finding is the ticket's newest closure record whose context child ran (`context_sync_id` is set), when that record was abandoned with `remote_branch_deleted`, is newer than the newest proven push of the context, and no fetch since has recorded the branch present. A deletion seen only by a plain push is not evidence here, because `republish_evidence`'s `Pushed` is any proven push with no fetch record, which every first publication has (ruling 50); it needs a poll first, or one `ticket close` that answers `remote_branch_deleted` (rulings 50 and 51a). Situation 3.1, which has no context, keeps `deleted()`, which counts a push too, since the publication never forces;
3. no context exists:
   1. its remote branch's deletion is evidenced: `new_branch`, retiring the remote history; `retired_oid` is the tracking tip, or else the newest proven push, and an earlier push that is not its ancestor blocks prepare with `history_unresolved`;
   2. a remote tracking ref of the ticket's branch exists and its tip is an ancestor of the tracking primary: `new_branch` without retirement; publishing its commit, a descendant of the tracking primary, fast-forwards the surviving branch (decision 6);
   3. a remote tracking ref exists otherwise: blocked with the new blocker `remote_context_unmaterialized`, whose way out is `PollOnce` (a tip only the local primary holds, which no poll materializes, is the same blocker with the way out `repo sync`);
   4. no tracking ref: `new_branch`;
4. the context's ticket holds a closure: `close` with closure `existing`;
5. otherwise: `close`.

Then the blockers, as the direct close's where they apply: not a ticket; an unfinished closure record on the ticket (`recovery_required`, naming its request, decision 33); an unfinished synchronization of the ticket's context (`busy`, naming it); a pending comment publication on the ticket (C12); the context nonconforming, dirty or conflicted; a synchronization conflict pending; a merge, rebase or cherry-pick in progress at the root (`WorktreeConflicted`); `history_unknown` and `history_unresolved` as the direct close reports them; no identity (`identity_required`). There is no blocker for the root's branch or cleanliness otherwise, because nothing touches the primary.

The digest binds the domain, the action, the item, the context branch, the primary branch, the remote, the context's head (or none), the closure effect (`record` with the `closed_by` text, or `existing` with both fields), and for `new_branch` the tracking primary, the old context's tip, a remote tracking ref's tip and the unheld entries (RFC: "the mode, the item, the branch, the remote, the target primary and the `closed_by` text"). It does not bind a `record` closure's `closed_at` (C6). The preview's details are a new `PreviewDetailsDto` variant, tagged `"type": "pull_request_closure_preview"`, holding the action, the item and its slug, the branches, the remote, the context and tracking-primary OIDs, the closure effect, the retired context and the unheld entries (Part F), and the `pull_request` object. The effects:

| Action | Effects |
| --- | --- |
| `close` | `context_synchronized`, `closure_recorded`, `context_published`, `pull_request_link` |
| `close`, closure `existing` | `context_synchronized`, `pull_request_link` (the synchronization publishes anything pending) |
| `withdraw` | `context_synchronized`, `closure_withdrawn`, `context_published` |
| `new_branch` | `worktree_removed` and `branch_deleted` (for an old context), `context_created`, `closure_recorded` (absent when kept), `context_published`, `pull_request_link` |

**Confirm, `close` action.** Built test-first against the tables below, with a design checkpoint.

1. Re-observe and compare the digest (`external_change` on a difference; nothing written; a situation that changed since prepare, for example to `remote_context_unmaterialized`, is a difference). `begin_record` with `integration_mode` `pull_request` and `action` `close`.
2. The context child, under `child()`. A child that cannot get past its stop with nothing written (`remote_branch_deleted`, or a child that ended) is let go and the record abandoned, its `answer_code` the child's code; a new `ticket close --prepare` offers what the evidence then shows (Part F after a deletion). Step `context_synchronized`.
3. Under the lease, the closure hook, after its reconciliation on a retry (`CheckoutDone`, `CheckpointWritten`), in this order:
   1. the tracking primary's ticket holds a closure: abandoned (`ticket_closed`, blocker `already_closed`), nothing written;
   2. the head's ticket holds a closure: for closure `existing`, if it is the consented one, the record goes to `closing` with no commit (`closure_oid` none, kind `existing`) and on to step 4; any other head (none, or another closure) is abandoned with `external_change`. For `record`, abandoned with `already_closing` (nothing written; the abandon upserts the link, as a completion does);
   3. otherwise: the identity against the consented `closed_by`; `closed_at` from the injected clock (R-23), stored; the closure commit built on the head with `closed_ticket_bytes`, unreferenced, `closure_oid` stored (step `closing`); the context moved with `move_context_to_checkpoint_with`; the contexts marked dirty and the index refreshed outside the lease.
4. The publication child, under `child()`, in `finish_steps`. Then the answer table below, then `complete_record` with the link upserted in the same transaction.

**The answer after the publication child**, in this order:

| After it | Answer | Record |
| --- | --- | --- |
| the tracking primary holds this record's closure | `ok` (the forge merged it, whatever the child answered) | `complete` |
| the tracking primary holds another closure | `ticket_closed` | `complete` |
| it stopped with `remote_branch_deleted` | `remote_branch_deleted`, way out `ticket close` again (Part F, keeping the closure) | `complete` |
| it stopped with `ticket_closed` (R-30) | `ticket_closed` | `complete` |
| it stopped because the publication remote changed or is gone | `recovery_required` with the `pull_request_closure` data (owner decision 16), way out `item sync` once the remote is set (R-35), derived from that data | `complete`; the commit stays on the local branch |
| the closure kind is `existing` | `already_closing` | `complete` |
| the head holds this record's closure | `ok` | `complete` |
| the head holds another closure | `already_closing` (Part G kept the published one) | `complete` |
| the head holds no closure (another clone's withdraw of this closure merged in) | `ok`, recording `withdrawn`: this record's closure was recorded and published, then withdrawn elsewhere (`withdrawn` with the action `close`; Part H, rulings 59 and 60) | `complete` |

Each row that follows a stopped child lets it go first. "This record's closure" is the closure at `closure_oid`'s ticket, or the consented `existing` one, compared on both fields. The row chosen is stored in `answer_code`.

**What a stop answers (R-5).** A child that stops answers as `item sync` answers that stop: the same code and data (host data, the tagged conflict data, or none), with the effects adding `write` and `checkpoint` `committed` once the context has moved, and the record stays unfinished. Its way out is the lifecycle's: the same request continues it (`request.retry`), as for a direct close; `request cancel` and Ctrl-C answer `cancelled` and leave it unfinished (decision 8). A conflict is resolved through the conflict verbs by the record's ID, which they map to its current child (both slots).

## Part E: Withdraw

`ticket withdraw-closure --id <ULID>`: a confirmed verb, `--prepare` and `--confirm` as close, no input, a branch record with the action `withdraw`, in either mode (decision 11), in a repository with a publication remote (`publication_remote_required` otherwise, R-33).

**Prepare.** Part D's blockers. A ticket with no context is `context_missing`. A context whose remote branch's deletion is evidenced is blocked with `remote_context_deleted` (the way out is `item republish`). A ticket whose context ticket and whose tracking ref's ticket both hold no closure answers `already_applied` with nothing to confirm and no data (decision 11); when only the tracking ref's ticket holds one, the withdraw is offered (its context child brings it in). Otherwise the digest binds the action, the item, the branch, the remote and the closure being withdrawn (both fields).

**Confirm.** As Part D's `close`, with step 3: the tracking primary's ticket holds a closure: abandoned (`ticket_closed`, blocker `already_closed`; withdrawing it would be a reopen); the head's ticket holds no closure: abandoned with `already_applied`; it holds another closure than the consented one: abandoned with `external_change`; otherwise the commit `Withdraw closure of ticket <ULID>`, whose ticket is the head's with both fields removed and serialized canonically (a new byte helper beside `closed_ticket_bytes`), built unreferenced, `withdraw_oid` stored (step `closing`), then the context moved; on a retry the generalized reconciliation keys on `withdraw_oid`. After the publication child, in this order: the tracking primary holds the withdrawn closure, or the published head holds a closure (R-30 restored it in a merge), or the child stopped with `ticket_closed`: `ticket_closed`; the child stopped with `remote_branch_deleted`: `remote_branch_deleted`, never `ok`; otherwise `ok` with the link record's link, or null when there is none. Each lets a stopped child go first. The link record is kept.

## Part F: The New Branch

Used in a pull-request repository by close for a ticket whose context's remote branch was observed deleted (decision 1, narrowed by decision 6), and for a ticket with no context (decision 7, Part D's situation 3). A branch record with the action `new_branch`.

**Prepare.** Besides Part D's blockers:

- the tracking primary must hold the ticket, open; otherwise an old context's case keeps the blocker `remote_context_deleted` (the way out is `item republish`) and a no-context case answers `context_missing`;
- an old context must be clean, unconflicted and at its branch's head, read as the existing blockers read it;
- `.manyhands/worktrees/<ULID>` must be free once the old context is counted out (`occupied_path` otherwise).

The preview names the tracking primary `P` the new branch starts from, the old context's tip `T` when there is one, and the **unheld entries**: each path whose entry in `T` differs from its entry in the one merge base of `T` and `P`, and also differs from its entry in `P`, with its change against `P` (`added`, `modified`, `deleted`), compared per path without rename detection, unbounded and sorted by path (R-19). An empty list means the content proof passes. History with no merge base or more than one is `recovery_required`. A new function in `proof.rs` computes the list from the existing private `entries`. A provisional closure the old context's ticket holds is kept (closure `existing`, R-21), and the digest binds it.

**Confirm.**

1. Re-observe and compare (`external_change` when `P`, `T`, a tracking ref's tip or the unheld entries changed). `begin_record` with `action` `new_branch` and `retired_oid` `T`. Under the lease: build the closure commit `C` on `P` (the ticket from `P`'s tree with the closure's fields: the kept closure, read from `T`'s tree now, or `closed_at` from the injected clock with the consented `closed_by`), store `closed_at` and `closure_oid`, and point `refs/manyhands/closures/<operation ULID>` at `C`, so that `C` and the kept closure survive anything that happens to `T`. From here the record holds the ticket (R-17).
2. With an old context, or published remote history (situation 2 or 3.1): the lifecycle's cleanup functions, in its order and with its checks. Under the lease, with no reservation: the full check (a refusal abandons the record with the cleanup's code and deletes the pending ref); step `worktree_removing`; remove the worktree (`remove_fresh_context_worktree` on the first attempt, `remove_context_worktree` after); step `worktree_removed`; delete the local branch; step `branch_deleted`. Then the parent's own remote reservation (action `close`), only for the remote part: re-check under it that the deletion is still evidenced and the tracking tip unchanged (otherwise abandon, deleting the pending ref), check local absence, delete the tracking ref if one exists, and in one transaction `retire_context`, the link deletion, step `retired` and the reservation's release (U-1). Nothing on the remote changes.
3. Under the lease: store step `closing`, then create `manyhands/ticket/<ULID>` at `C` (absent: create; at `C`: keep; anything else cannot be made by a Manyhands write while the record holds the ticket, and is `recovery_required`), add its worktree if missing, delete the pending ref, mark the contexts dirty and refresh the index outside the lease. ## Part G: Two Clones

**Settling a closure-only conflict (decision 2, R-13).** In a remote synchronization of a ticket context, the merge of the remote copy into the local branch (the Context stage) settles a conflict itself when all of these hold:

1. the only conflicted path is the ticket's own `ticket.md`;
2. the local (ours) and remote (theirs) tickets both parse and both hold closures, and the two closures differ;
3. the stage's fetched primary (`DivergenceInputs`) holds no closure of the ticket;
4. with ours' ticket rewritten to hold theirs' closure (canonically, through a new byte helper that replaces the fields of a closed ticket), the three-way merge of that path is clean.

The result is the clean merge of step 4, so the remote branch's closure (the one published first) is kept and the local one dropped. The function lives in `integration/prepare.rs` with R-30's rewrite and returns `MergePreparation::Clean`; it is called in `integrate_divergence` where `prepare_clean_merge` returns `Conflict` (Part G) or `Clean` (R-30), before any conflict is installed. A ticket that does not parse is left to the existing path.

Each test sits at the cheapest layer that catches its regression (AGENTS.md). ## Rulings

Each: decision — why — cost if wrong.

- **R-1** The pull-request close, withdraw and new branch are branch records of `ticket_closures`, run by the lifecycle with branches on the record's path in `promote_inner`, `finish_steps`, the hook and the outcome types (decision 13) — the lifecycle's attempts, holds, cancel, abandon, attribution and listing then serve them unchanged — the runner's shared code gains path branches that document promotion also compiles through.
- **R-2** A record's `integration_mode` and `action` are fixed when it begins; prepare chooses the observation by the configuration, and the branch observation's digest has its own domain, so a mode switch between prepare and confirm is `external_change` — Cycle 01 decision 11 — a switch costs a re-prepare.
- **R-3** The publication child uses the record's second child slot with a new `ChildRole::Publication` — every list of Baseline Fact 12 reads the slot's columns by name, so none changes — the places that read the slot as the primary (Baseline Fact 10) must branch on the path.
- **R-4** Branch records are listed, attributed, cancelled and resumed as closures are today, as the action `close` — Baseline Fact 12 — a withdraw shows as a `close` in `operation list`, with its step.
- **R-5** A child's stop answers as `item sync` answers it, with the lifecycle's way out (the same request) — the host and conflict actions then work unchanged — the stop's data does not say which step stopped; the operation list does.
- **R-6** The closing state is derived from the two copies in both modes, and the primary's closure, when its copy holds one, decides `closed` and is shown — the RFC (decision 11) — an interrupted direct close reads `closing` where it read `closed`.
- **R-7** The primary's copy is the row at rank `PRIMARY_COPY`, normally the root's working tree — it is what the index stores — an uncommitted closure in the root reads `closed` while the guard reads the branch tips, and a root checked out on another branch shows that branch's copy (K-9).
- **R-8** A new reason `closing_dependency` — the RFC says `ticket ready` and `ticket blocked` say so — one more enum value.
- **R-9** `ticket plan` computes with closing tickets as open, removes them from batches and `unplannable` as a filter removes tickets, each batch keeping its number (decision 15); `ticket critical-path` gives them no length — decision 9 — a dependent of a closing ticket sits in a batch without its blocker shown.
- **R-10** The guard reads the configuration's mode at each call, and `context_release` stays direct — RFC — a repository switched to direct with a provisional closure on a branch refuses writes to that ticket until a direct close merges it.
- **R-11** A save whose closure fields differ from the branch head's is refused with `invalid_input`, in both modes — the precheck no longer refuses a file that reads `closing` — a person who hand-edits those fields gets `invalid_input`.
- **R-12** Immutability is checked across the three sides at the validators, against a ticket context's pinned stage's fetched primary; today's rule elsewhere — primary targets and local synchronizations pin today's rule (Baseline Fact 7) — a resolution made before a fetch may drop a closure the forge has merged; R-30 stops its publication.
- **R-13** Only a closure-only conflict settles itself, keeping the remote's closure, in `prepare.rs` — decision 2 — the local `closed_at` and `closed_by` are lost without notice.
- **R-14** One helper deletes the link record, called by `retire_context` and `finalize_index`'s retiring branch — Baseline Fact 17 — a later retirement path must call it too.
- **R-15** `pull_request` and `closure.publication` are filled only by `ticket show`; `publication` is null in direct mode — lists read the index, and a direct branch-only closure is never published — every item golden changes once (E-4).
- **R-16** `already_closing` is class `None` with outcome `success`, appended last — decision 4 — a caller that expects `noop` for nothing written sees `success`.
- **R-17** The hold of an unfinished branch record is the C1 fence extended: `closure_holds_context` exempts the record's own publication child, and the writers' guards and `context retire` also refuse while it holds — decision 8 — comments and saves on that ticket wait for its request to run again (K-4). The exemption is by the child's identity, its synchronization ID, so it also covers a `conflict resolve` continuation of exactly that child and an `operation resume` of it, each by the child's own synchronization ID (rulings 67 and 68; a resume by the record's ID answers `original_request_required` when its request holds it, ruling 64a): the resolve then gets past the hold, publishes the child, and the record's same request finishes (R-5). `item resolve-history` is not refused by the hold (ruling 19).
- **R-18** Abandon, not supersede, ends a branch record that cannot continue before its commit (a context child that cannot get past its stop, a consent difference, a refusal at step 3) — as the direct close (Baseline Fact 8) — none.
- **R-19** The unheld entries are computed per path against the one merge base, without rename detection, unbounded — the preview already lists the whole branch's changes — a rename shows as a deletion and an addition.
- **R-20** The new branch starts from the tracking primary as last fetched, bound by the digest — prepare reads local state only — a stale tracking primary gives a pull request behind the primary.
- **R-21** The new branch keeps a provisional closure the old context held, read from `T` at step 1 into the commit `C`, which a pending ref holds until the branch exists — the record does not hold `closed_by`, and `T` is unreferenced after the retirement — one more ref while the record is unfinished.
- **R-22** The desktop gets compile-level arms only — Cycle 06 owns its design — the desktop shows a closing ticket as open, offers "Close ticket" (answering `already_closing`) and shows a generic preview.
- **R-23** The runner takes its clock as a parameter, and production passes the wall clock — AGENTS.md — none.
- **R-24** One SSH case (decision 11), and the new verb's conformance row in the `Confirmation` home with rules 1 and 2 exempt — a `Remote` home would need a second SSH case — those two rules are pinned only by P14.
- **R-25** The link is built from the publication remote's URL as `git2` reports it; P14 configures a `[forge] pull_request_url` template — the harness's URL is no forge's — an unusual URL gives no link, never a failure.
- **R-26** Cycle 02's `pull_request` schema and DTO are reused, or added identically — decision 5 — a merge of two identical files.
- **R-27** Step 3 and the answer table check the tracking primary; reads and the guard check the local primary — the tracking primary is fresher after a synchronization — after a forge merge and before the local primary moves, the ticket reads `closing` while withdraw refuses it (K-7).
- **R-28** The new verb is delivered under the label `C5` and sits in `ticket close`'s autonomy column — a later verb joined `C5` before (vh-hyksw) — none.
- **R-29** `item sync`'s link is new tagged data only when it publishes or finds current a closing ticket's branch in a pull-request repository — decision 12 — one more data shape for `item sync`'s callers.
- **R-30** A ticket context's synchronization does not publish a head lacking a closure the primary it fetched holds: a clean merge is given it, and otherwise the push is refused with `ticket_closed` — RFC decision 20, in every merge style (decision 10) — a withdraw that raced the forge's merge stays local, and one that raced it after the fetch is published until the next synchronization restores the closure.
- **R-31** The new branch's local removals run under the lease with no reservation; the parent's own remote reservation (action `close`) is taken only for the tracking ref's deletion and the retirement's transaction, which releases it and records step `retired` — `delete_tracking_ref` needs a held reservation, and a reservation held across local removals would block the repository on any stop there — a new release transition beside `finish_parent` (U-1).
- **R-32** Withdraw's `already_applied` keeps `noop` although its context child may have published — the effects show the publication — a caller reading only the outcome misses it.
- **R-33** Withdraw needs a publication remote, in either mode — its children publish — a local-only direct repository cannot withdraw (it has no branch-only closures outside an unfinished direct close).
- **R-34** The branch hook is built from the direct hook's parts without its base checks, and its reconciliation is generalized to the record's written commit — the direct hook prepares a merge into the base, which a branch record never makes — the parts' preconditions must hold without a `LeasedIntegration` (Task 7's design checkpoint).
- **R-35** A branch record whose publication remote changed or is gone completes, leaving its commit on the local branch, with `recovery_required` carrying the `pull_request_closure` data, and the way out `item sync` (`manyhands-cli item sync --repo R --id I`), derived from that data (owner decision 16) — its commit is meant to be published, so leaving it local loses nothing, and C9 forbids abandoning it — the person publishes it once the remote is set.
- **R-36** Branch records are never superseded, and every completion lets a stopped child go first — the direct close's rule (Baseline Fact 8) and decision 8; a stopped child left behind would hold the repository — none.

## Known Limits

The Cycle document's K-1 to K-14. K-1 to K-11 are as approved. Amended 2026-11-26 at Task 15, from rulings made during implementation:

- **K-12** (ruling 47) A process death at the TRACKING or COMMIT seam of a new branch's retirement leaves the tracking ref's `.lock`, as it does for the direct close. The record then stops with `recovery_required` until an operator removes the lock, and the same request then continues.
- **K-13** (ruling 71) Once the ticket branch is gone, a same-request replay of a finished close or withdraw answers `recovery_required` unless the primary holds the commit: a merge commit or a fast-forward replays, a squash or rebase merge does not. `ticket save` and `comment add` meet the same limit.
- **K-14** (ruling 72) A replay of an `operation resume` that finished a branch record is still read at the primary, because its stored result names no item. It answers `recovery_required` while only the ticket branch holds the commit.

## Unverified

- **U-1** The transition that releases the parent's `close` reservation in the new branch's retirement transaction without completing the record (`reservation.rs` `finish_parent` and `finish_remote_operation`, about 1204 and 2182; a completed row then replays). Task 9's design checkpoint names it; if no existing transition can be generalized, it stops for the owner.

## Design Checkpoint Obligations

Round 4's source review listed the adaptations the lifecycle needs for branch records. They are required, and the design checkpoints of Tasks 7 to 9 write each one down before code, checked against the source:

1. **Path accessors.** `ParentRecord`/`LifecycleRecord` gain the record's path (with a direct default for promotion); `ParentFacts` carries the closure step and the path; `effect_written`, `written_checkpoint` and `merged_context` read the path (`withdraw_oid`; `retired_oid` for the retirement); `promote_inner`'s resume dispatch routes by path and step, not by `integration_oid`.
2. **The branch hook** (R-34), with `base_oid` stored as the tracking primary it read, and `begin_closing`'s variant per action.
3. **The rebuild**: the frozen v2 DDL, the explicit column list, the marker on the created path, the per-action CHECKs, `answer_code`, the step `retired`.
4. **Completion and answers**: the branch completion function; `answer_code` for every finished branch record, abandon included, read by re-entry and replay; `TicketClosureOutcome`, `make_outcome`, `run_observed`, `Reached` and `closure_reached` without an integration.
5. **The withdraw lifecycle**: withdraw is its own `Lifecycle` implementation over `ClosureRecord` (KIND `TicketClosure`), so `preview_request` and `prepare` observe a withdraw at confirm and on resume; `new_branch` is chosen by the close observation's situation.
6. **R-30's placement** in the push decision, its ending rule, and its test seam (a test that drives the push decision; `promotion_test_drive_local_bound` runs only `integrate_divergence`).
7. **The publication child's error** returned by `finish_steps` for a branch record (R-5).
8. **The binding's sites**: `bind/lifecycle.rs` `Stages` (an exhaustive `ChildRole` match), `held_by_its_child` (the new verb), `parent_effects` and `ParentView` (the path and `withdraw_oid`), `bind/mod.rs`'s recorded effects for a lifecycle parent, `lifecycle_verb.rs` `closure_reached`, `way_out.rs` rows for branch data, and `mutate.rs`'s retry guard.
9. **The conflict lookups' "current" child**: the publication child once `primary_attempt > 0`, the context child before.
10. **No new closure blocker**: a confirm whose situation changed is `external_change`, so `ClosureBlocker`'s full mask is unchanged.
11. **Reuse Cycle 01's `Integration`** for `integration_mode`.

## Alternatives Rejected

- A separate runner and record (revisions 1 to 3): three review rounds found the direct close's rules missing from it one at a time (decision 13).
- A third `LifecycleKind`: the remote action CHECK and every two-table list would change; a branch record keeps `ticket_closures` and its lists.
- Replacing a surviving remote branch: decision 6.
- Ending a stopped close on `request cancel`, or superseding it: decision 8 and R-18.
- Listing closing tickets in `ticket ready`: decision 9.
- `closed_by` in the answer: decision 10.
- Relaxing immutability for every synchronization: R-12.
