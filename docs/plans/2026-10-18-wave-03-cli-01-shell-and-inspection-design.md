## Intent And Approval Boundary

This design implements the [C1 Cycle](../Cycles/wave-03-cli-01-shell-and-inspection.md).
Where they disagree, the Cycle governs, and the disagreement is a defect to
fix in this document. Decisions are referred to by their Cycle number
("decision 3").

C1 adds a command-line front end over F1's read services. It adds no domain
behavior. Every read result is produced by an existing F1 method and
serialized through F1's envelope; C1 owns parsing, dispatch, human rendering,
exit statuses and help.

## Baseline Facts

Checked at `f6a4c06` on 2026-10-18; Task 0 re-checks them at the
implementation baseline.

- `src/bin/manyhands-cli.rs` has seven lines. It calls
  `manyhands::runtime::initialize_git_transport_before_threads()`, prints
  `Git transport initialization failed` to stderr and exits 1 on failure, and
  otherwise exits 0 silently. It reads no arguments.
- `Cargo.toml` declares the bin at that path with no required feature, has

  `Envelope::failure(command, scope, code, recovery)` build failures.
  `Envelope::failure_class()` returns the class a front end maps to its exit
  status. No function maps a class to a number.
- `ResultCode` is generated by the `result_codes!` table in `src/results.rs`.
  `src/repository/mutation/outcome.rs` has an exhaustive `match code` at
  line 719 with no wildcard arm.
- Existing tests pin the code list: `src/results_tests.rs`
  `DESIGN_CODES` (68 entries) and `result_code_messages_are_fixed`;
  `tests/read_contract.rs` checks that the `code` enum in
  `schemas/v1/envelope.schema.json` and the `result.code` enum in
  `schemas/v1/request.schema.json` equal `ResultCode::ALL`.
- `canonical::ItemId: FromStr`, `SharedKeyId::parse` and
  `OperationId::parse` reject anything but a canonical ULID. There is no
  conversion from their errors to `ReadError`; `ReadError::invalid_id()`
  exists.
- `SshAuthority { host: String, port: u16 }` has public fields and no

- `tests/support/golden.rs` fixes its directory to `tests/fixtures/read_v1`
  and refuses cases not listed in `CASES`. `tests/support/mutation_golden.rs`
  keeps a second directory with its own cases, reusing `golden::render` and

  - `tests/mutation_contract.rs`:

- `resolve_repository` opens a read session, and the session requires a
  readable index. So every repository-scoped read fails with

  service opens, before any read.

## Module Layout

```text
src/bin/manyhands-cli.rs            entry point: main() only
src/bin/manyhands-cli/
  catalog.rs                        every RFC command, its availability and inputs
  parse.rs                          clap tree from the catalog; Invocation
  startup.rs                        transport start, data directory, service open
  dispatch.rs                       one function per available verb
  render.rs                         JSON and human output, streams, exit status
  human.rs                          human text for each DTO
  *_tests.rs                        unit tests beside each module
```

Rust resolves `mod catalog;` in `src/bin/manyhands-cli.rs` to
`src/bin/manyhands-cli/catalog.rs`, so the bin keeps the path AGENTS.md and
`Cargo.toml` name. Nothing CLI-specific enters `src/lib.rs`, so the desktop
binary does not compile it.

`clap` is added as a direct dependency with default features off and
`std`, `help`, `usage` and `error-context` on. Without the `color` feature
there is no colour, and the colour methods (`Command::color`,
`disable_colored_help`) do not exist, so they are not called. Without
`wrap_help`, clap does not read the terminal width. The root command sets
`.bin_name("manyhands-cli")`, so help reads the same on Windows, where argv[0]
ends in `.exe`.

`src/bin/manyhands-cli.rs` carries `#![allow(clippy::result_large_err)]`, as
`src/repository/read/mod.rs` does, because the bin passes `ReadError` in
`Result`s.

## Startup Order

`main` does exactly this:

1. Collect `std::env::args_os()`.
2. Parse (see "Parsing"). Parsing starts no thread and no native Git.
3. If the invocation is help, version, the bare call, a usage error or an
   unavailable command: write the result and exit. Neither the transport nor
   the data directory is touched.
4. Otherwise call `initialize_git_transport_before_threads()`. On failure,
   write an `internal_error` envelope for the parsed command and exit 1. In
   human mode stderr also says `Git transport initialization failed`.
5. Resolve the data directory (see "Data Directory") and open the service.
   A `RepositoryError` becomes a failure through `ReadError::from`.
6. Dispatch the verb, write its result, exit with its status.

This keeps the pre-thread boundary: nothing before step 4 starts a thread or
calls libgit2, and every command that can reach Git starts the transport
first. The Wave's sentence that bootstrap runs "before argument handling"
described the old seven-line main; the requirement it protects is the
pre-thread boundary, and the RFC requires help and version without
starting services.

The order is testable: `startup.rs` exposes a small `Startup` trait
(`start_transport`, `open_service`) that `main` implements with the real
calls, and unit tests drive `run` with a fake that records the calls.

## Parsing

### Options

| Option | Where | Value |
| --- | --- | --- |
| `--json` | global, before or after the command | flag |
| `--non-interactive` | global | flag; no effect in C1 |
| `--repo <path>` | per verb | path; relative to the invocation directory |
| `--id <ULID>` | per verb | canonical item ULID |
| `--key-id <ULID>` | `key show`, `key public` | canonical key ULID |
| `--operation-id <ULID>` | `operation show` | canonical operation ULID |
| `--authority <host[:port]>` | `host inspect` | see below |
| `--path <path>`, `--context <path>` | `document show`, `ticket show` | repository-relative path; context worktree path |
| `--status`, `--type`, `--project` | `ticket list`, `ready`, `blocked`, `plan` | exact text |
| `--closure open\|closed\|all` | `ticket list` | default `all` |
| `--slug <code>` | `ticket list` (filter), `ticket find` (required) | text, passed through |
| `--ready`, `--blocked` | `ticket list` | flags; at most one |
| `--direction down\|up\|both` | `ticket deps` | default `down` |
| `--depth <n>` | `ticket deps` | unsigned integer |

Only `--json`, `--non-interactive`, `--help` and `--version` are global,
matching the RFC synopsis, where they precede the resource and every other
option follows the verb. `--input`, `--request-id`, `--prepare` and
`--confirm` are not declared on any available verb, so supplying one is a
usage error.

clap setup on every command in the tree:

- `disable_help_flag(true)`, `disable_help_subcommand(true)` and
  `disable_version_flag(true)`. clap's own help and version are reported as
  errors (`ErrorKind::DisplayHelp`), and its `help` subcommand would add
  commands the catalog does not have. Instead, global `--help` and
  `--version` flags (`ArgAction::SetTrue`) are declared on the root.
- `args_override_self(true)` on the root, so a repeated flag such as
  `--json --json` is accepted, not an error.
- `subcommand_required(false)` on the root and on each resource, so a bare
  call or a bare resource parses instead of erroring.

After a successful parse, the action is decided in this order:

1. `--help` set, or found by the raw scan below: `Help` for the matched
   command, the matched resource, or the root.
2. `--version` set: `Version`.
3. No resource: `Help` for the root (the bare call).
4. A resource with no verb: `Help` for that resource, exit 0.
5. A planned verb: `Unavailable`.
6. An available verb whose per-verb rules (below) fail: `Usage`.
7. Otherwise: `Run`.

A clap error (unknown command or option, bad value, missing value) is
`Usage`, unless help was requested: when `help_requested(&args)` is true,
help wins even over a clap error, and its target comes from the raw scan in
"The `command` field" (a catalog command, else a known resource, else the
root). So `frobnicate --help` is root help, exit 0.

No option is marked `.required(true)` in clap. Required options are checked
by the per-verb rules after parsing, so `ticket deps --help` is help, not a
missing-argument error.

A value option given twice keeps its last value (`--id A --id B` uses `B`),
because `args_override_self` applies to every argument. This is accepted and
tested.

Per-verb rules, enforced after clap parsing:

| Verb | Required | Refused |
| --- | --- | --- |
| `repo list`, `key list`, `host list`, `id new` | — | `--repo` |
| `key show`, `key public` | `--key-id` | `--repo` |
| `host inspect` | `--authority` | `--repo` (decision 7) |
| `document show`, `ticket show` | `--repo`, and exactly one of `--id` or `--path` | `--context` without `--path` |
| `comment list`, `ticket deps`, `ticket children` | `--repo`, `--id` | — |
| `operation show` | `--repo`, `--operation-id` | — |
| `ticket find` | `--repo`, `--slug` | — |
| `ticket list` | `--repo` | `--ready` with `--blocked` |
| every other C1 verb | `--repo` | — |

A missing required option, a refused one or a pair that conflicts is a
`usage_error`. clap declares the options each verb takes; the table's extra
rules are checked by one function over the parsed matches.

### Values

- `--id` parses with `ItemId::from_str`, `--key-id` with
  `SharedKeyId::parse` and `--operation-id` with `OperationId::parse`. A
  failure is `ReadError::invalid_id()`, exit 2. Parsing happens in dispatch,
  after the service opens, so the failure is an F1 envelope like any other.
  A short code therefore fails as `invalid_id`, as the relationships RFC
  requires.
- Order and scope: a repository-scoped verb resolves `--repo` first, then
  parses its IDs, and an ID failure carries `repo.scope()`
  (`ReadError::invalid_id().with_scope(repo.scope())`). This matches F1's
  golden `failure_invalid_id`. So a bad `--id` with an unregistered repository
  is `repository_not_registered`. `--key-id` belongs to application-global
  verbs, and its failure keeps the default scope.
- `--authority` is `host`, `host:port`, or `[address]` / `[address]:port`
  for IPv6. The port defaults to 22. A port that is not 1–65535, an empty
  host, or anything else that does not fit is a `usage_error`. IPv6 brackets
  are stripped, so `[::1]:2222` becomes `SshAuthority { host: "::1", port:
  2222 }`: F1's `stored_authority` adds brackets itself, and a bracketed host
  would never match. Other hosts are passed as written; F1 normalizes their
  case.
- `--closure` and `--direction` use clap's value lists; a bad value is a
  `usage_error`.
- `--depth` is a `u32`; anything else is a `usage_error`.
- `--slug` is passed to F1 unchanged. An empty or malformed code matches
  nothing, and the result is an empty list with exit 0, which is F1's and the
  relationships RFC's behavior.
- An argument that is not valid UTF-8 is a `usage_error`.

### Unavailable commands

Each planned command is declared to clap with one trailing argument that
accepts any values, including ones that look like options. So
`ticket close --id X --prepare` parses as the command `ticket close`, and the
result is `command_unavailable`, not a complaint about `--prepare`.

### Recognizing `--json` and `--help` from the raw arguments

A planned verb's catch-all argument captures everything after its first
unknown option, including a later `--json` or `--help`. And a clap error
reports neither. So, whatever clap returns:

- JSON mode is `matches.get_flag("json") || json_requested(&args)`.
- Help is requested if `matches.get_flag("help") || help_requested(&args)`.

Both scans look for an argument exactly equal to the flag, before a literal
`--`. Abbreviations and `--json=...` do not count.

### The `command` field

- A parsed command, available or not: `<resource> <verb>`, for example
  `ticket list` or `ticket close`.
- Help and version: `cli help` and `cli version`, including a command's or a
  resource's own help.
- A usage error: the command named by the first two arguments that are not
  options (skipping the global flags), if they are a catalog command;
  otherwise `cli usage`. clap's error does not say which subcommand failed,
  so this scan names it.

## Result Codes

Two codes are added to the `result_codes!` table:

| Code | Class | Message |
| --- | --- | --- |
| `usage_error` | Input | `The command line is not valid; see --help.` |
| `command_unavailable` | Input | `That command is not available in this version of the CLI.` |

Both have no recovery action: they join the no-action arm of the `match` in
`src/repository/mutation/outcome.rs` (decision 9). They are added to:

- the envelope schema's `code` enum and the request schema's `result.code`
  enum, after `invalid_input` in both, matching their position in
  `ResultCode::ALL`;
- `DESIGN_CODES` and the list in `result_code_messages_are_fixed` in
  `src/results_tests.rs` (named edits 1 and 2). `DESIGN_CODES`' doc comment,
  which describes the order of its groups, gains a sentence for the CLI
  codes.

Their evidence in the shared contract tests (decision 11):

- `golden_envelopes()` in `tests/mutation_contract.rs` also reads every JSON
  case of `tests/fixtures/cli_v1` (named edit 3). The CLI's usage and
  unavailable goldens then satisfy
  `every_result_code_has_a_golden_or_a_reason_no_fixture_can_produce_it`,
  and the help and version goldens satisfy the data-root test.
- `DATA_ROOTS` gains `cli_help.schema.json` and `cli_version.schema.json`
  (named edit 4).
- `CODES_NO_MUTATION_GOLDEN_HAS` gains both codes with the reason "a CLI
  parse result; no command of execute or prepare returns it" (named edit 5).
- `contract_enumerations()` in `tests/read_contract.rs` gains one entry,
  `("cli_help_command.schema.json", "repository", ["required", "refused"])`
  (named edit 6). The helper walks only `properties`, never an array's
  `items`, so each help command has its own schema reached by `$ref`, and it
  leaves `null` out of the expected list itself. The list comes from
  `CLI_REPOSITORY_VALUES` in `tests/support/cli.rs`. The tests cannot reach
  the bin's constants, so the tie to the binary is a CLI test: the root
  JSON help uses exactly `required`, `refused` and null across its commands.

Because the usage and unavailable goldens are the codes' evidence, the codes,
their schemas entries, the CLI harness and those first goldens land in the
same task, so no commit leaves these tests red.

A usage error or unavailable command envelope has an empty scope, null
`data` and no recovery. In human mode, stderr adds clap's own explanation of
a usage error, without colour, and for an unavailable command the Cycle that
delivers it (for example `ticket close arrives with C5`). The JSON `message`
stays the fixed message, as for every code.

## Help And Version

Text help is generated by clap from the catalog. The root help lists every
resource and verb, marking planned ones with the Cycle that delivers them.
A command's `--help` shows its options; a planned command's `--help` says
which Cycle delivers it. The bare call prints the root help. All exit 0.

Under `--json`, help and version are success envelopes with no scope and
no effects.

`cli help` data, schema `cli_help.schema.json`:

```json
{
  "commands": [
    {
      "command": "ticket list",
      "available": true,
      "delivered_by": "C1",
      "summary": "List tickets, open and closed unless filtered.",
      "repository": "required",
      "options": [
        {"name": "--closure", "value": "open|closed|all", "required": false, "summary": "..."}
      ]
    }
  ]
}
```

The root help lists every command, a resource's help lists that resource's
commands, and a command's own help lists just that command. `repository` is
`required` or `refused` for an available command, and null for a planned
one, whose `options` are empty (decision 13). `value` is null for a flag.
Text help for a planned command shows its name, its summary and
`Arrives with <Cycle>.`

Three schemas describe it: `cli_help.schema.json` (the root, an array of
`$ref` items), `cli_help_command.schema.json` and
`cli_help_option.schema.json`. The command schema writes `repository` as
`"type": ["string", "null"], "enum": ["required", "refused", null]`, and it
is registered in `contract_enumerations()` (named edit 6).

The version golden contains the package version (`0.1.0` at this baseline).
Placeholders must be at least eight characters, so a version bump
regenerates the `version` and `version_text` fixtures; that is accepted.

`cli version` data, schema `cli_version.schema.json`:

```json
{"name": "manyhands-cli", "version": "<CARGO_PKG_VERSION>"}
```

The contract version is the envelope's own `schema_version`, so the data does
not repeat it. An integer enumeration could not be registered with the
enumeration test anyway.

Text version prints `manyhands-cli <version>`.

## Data Directory

- `MANYHANDS_DATA_DIR` unset: `RepositoryService::open_default()`.
- Set and non-empty: an absolute path is used as it is; a relative path is
  joined to the current directory. Then `RepositoryService::open_at`.
- Set and empty: `invalid_path`, exit 2, before anything is opened.

`open_at` creates the directory if it is missing, as F1's read contract
allows. The variable is documented in the CLI RFC and in `--help` as an
advanced and testing override. The library is unchanged.

## Dispatch

One function per available verb. Each resolves `--repo` with
`resolve_repository` (if the verb takes it), parses IDs, calls one F1
method, and returns the DTO with the command name. A `ReadError` becomes a
failure envelope through `to_envelope`.

| Command | F1 call |
| --- | --- |
| `repo list` | `list_repositories()` |
| `repo inspect` | `inspect_repository(path)` (no resolution; it works on unregistered repositories) |
| `repo identity` | `repository_identity(&repo)` |
| `remote list` | `list_remotes_redacted(&repo)` |
| `key list`, `key show`, `key public` | `list_keys()`, `show_key(id)`, `public_key_text(id)` |
| `host list`, `host inspect` | `list_host_pins()`, `inspect_host(&authority)` |
| `document list`, `folder list` | `list_documents(&repo)`, `list_document_folders(&repo)` |
| `document show`, `ticket show` | `show_item(&repo, &id)`, or `show_path(&repo, context, path)` |
| `ticket list` | `list_tickets(&repo, &filter)` |
| `ticket ready`, `ticket blocked` | `ticket_readiness(&repo, &filter)` with `readiness` set |
| `ticket deps` | `ticket_dependencies(&repo, &id, direction, depth)` |
| `ticket children`, `ticket cycles` | `ticket_children(&repo, &id)`, `ticket_cycles(&repo)` |
| `ticket plan`, `ticket critical-path` | `ticket_plan(&repo, &filter)`, `ticket_critical_path(&repo)` |
| `ticket find` | `find_tickets_by_slug(&repo, slug)` |
| `comment list` | `list_comments(&repo, &id)` |
| `index status`, `poll status` | `index_status(&repo)`, `polling_status(&repo)` |
| `operation list`, `operation show` | `list_operations(&repo)`, `show_operation(&repo, id)` |
| `id new` | `new_item_id()` |

The scope of each success is what F1's golden tests use for the same read:
`repo.scope()` for repository reads, with `item_id` set for reads of one
item, and `Scope::default()` for application-global reads. The plan's verb
tasks copy the exact scope each golden test in `tests/read_contract.rs` uses
for the same read.

`index status` cannot report `state: unavailable` through the CLI: the
repository resolves first, and resolution needs a readable index. F1's
`index_status_unavailable` golden therefore has no CLI counterpart (Cycle
ruling R-2).

**Kind of item (decision 10).** `document show --id` returns
`item_not_found` when the item is a ticket, and `ticket show --id` when it
is a document. A by-path `show` of the wrong kind of file is the same. The
check is in dispatch, on the returned DTO's `kind`, so the F1 read is
unchanged. The failure's scope is the scope the success would have had:
`repo.scope()` with the item ID for `--id`, and `repo.scope()` alone for
`--path`.

## Output And Exit Status

`render.rs` turns a result into bytes and an exit status:

- **JSON mode.** One object, serialized with `serde_json::to_string` (compact,
  field order as F1 serializes it), then a newline, to stdout. Nothing is
  written to stderr.
- **Human mode, success.** The human text to stdout. A list whose index is
  `stale` or `never_refreshed`, or whose `complete` is false, also writes one
  note line per condition to stderr. Each renderer returns
  `Human { stdout: String, notes: Vec<String> }`, so it can report those
  conditions from the DTO it knows.
- **Human mode, failure.** To stderr: the message, the code, and one line per
  recovery action naming the action and its arguments.

Exit status:

| Envelope | Exit |
| --- | --- |
| success or noop | 0 |
| class Input | 2 |
| class Blocked | 3 |
| class Incomplete | 4 |
| class Transient | 5 |
| class Internal | 1 |
| class Cancelled | 130 |

The mapping is one `match` over `FailureClass` with no wildcard arm.

A failed write to stdout or stderr, including a closed pipe, ends the
process with exit 1 and writes nothing more. The process never panics on
output.

## Human Text

Human output is for reading, not parsing. Rules:

- Every ticket is shown with its ULID and, when it has one, its short code
  beside it.
- A nonconforming entry is shown by path, marked `nonconforming`, with its
  problem codes.
- A closed ticket is marked `closed`, whatever its status text.
- Times are printed as the DTO has them.
- `key public` prints only the public key text, so it can be piped.
- `id new` prints only the ID.
- A `show` prints its metadata as `Name: value` lines, a blank line, then the
  body; a nonconforming item prints its source instead.
- `ticket deps` indents each line by its depth and marks a repeated ticket.
- `ticket plan` prints numbered batches, then the unplannable tickets with
  their reasons.
- `ticket blocked` prints each ticket's reasons under it.
- `comment list` indents each comment by its depth.
- An empty list prints nothing on stdout and exits 0.

Four human outputs are pinned as golden text: root help, version, one
`ticket list`, and one failure (`item_not_found`). The rest are checked for
content (IDs and codes present, no secret) rather than layout.

- Stale reads:

The exit-class coverage test is table-driven. Each row is a command line
with its expected code and exit, run through the binary in that test. Class
coverage is asserted over the table, so the table cannot drift from what
runs.

`busy` needs a child process that holds the lock. `tests/cli.rs` defines a
top-level `#[test] fn index_lease_child()`, copied from
`tests/read_boundary.rs:34-58`, and the test starts it with the public
`support::hold_lease_in_child_for_test`. `busy` can come back with an empty
or a repository scope, because the service open and the resolution both
take the lock.

## Alternatives Rejected

- **clap derive.** The catalog would be duplicated between attributes and
  the table; the builder takes the table directly.
- **CLI code in the library.** The desktop binary would compile it.
- **A `--data-dir` flag.** It would add to the approved grammar (decision 2).
- **Parsing after transport start.** Help would start a service, which the
  RFC forbids.
- **Validating `--slug` in the CLI.** F1 and the relationships RFC already
  define an unmatchable code as an empty result.

## Risks

| Risk | Control |
| --- | --- |
| clap's help or error text varies with terminal width or version. | No colour, no terminal-width feature, a test comparing help under different `COLUMNS`, `Cargo.lock` pins the version. JSON messages never contain clap text. |
| A planned command's catch-all argument swallows a mistake in an available command. | Only planned commands have it; a test passes an unknown option to an available command and expects `usage_error`. |
| A DTO change in F1 breaks a human renderer. | Renderers use the DTO fields, so a change is a compile error. Most human text is not pinned. |
| A test touches real data or Git configuration. | Every child gets the isolation environment; a test checks the platform-default case creates its directory only in the temporary location. |
| The two new codes affect mutation behavior. | They only join the no-action arm; the existing outcome tests, which loop over every code, cover them. |
| Adding codes is read as a contract break. | Adding a code is non-breaking under the v1 rule (F1 decision 8). |
| A broken pipe panics. | Writes go through one function that maps every error to exit 1. A test closes the child's stdout early. |
