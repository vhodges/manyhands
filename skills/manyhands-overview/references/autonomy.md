The owner set this policy on 2026-11-17. Every other skill defers to it and does not restate it.

## Showing the person a prepared preview

Run the verb with `--prepare`. It changes nothing and answers with a confirmation ID, an expiry (about ten minutes) and the effects it will have. Show the person the preview in plain words: what will be created, merged, removed or trusted, and for `host approve` and `replace` the fingerprint itself, copied from the answer and never summarized. Ask for their OK and wait. Only then run the same command with `--confirm <confirmation-id>` and a fresh `--request-id`. If the person says no, or the expiry passes, drop the confirmation and prepare again if they change their mind.

Only some verbs are confirmable. Any other verb answers `--prepare` with `not_confirmable` (exit 2) and has no preview. Of the verbs in the middle column, `key generate`, `key import`, `operation resume`, `context retire` and `poll once --retire-completed` are such verbs: describe the action in your own words and wait for the person's OK before you run it. Every other verb follows its own column of the table, whether or not it has a preview: `key select` and `remote add` you run alone, and `key remove`, `key delete` and `repo remove` you hand to the person and never run to completion yourself, even after an OK.

For a hand-over verb that has a preview (`key delete`, `repo remove`, and the others in the third column that accept `--prepare`), you may run `--prepare` so you can show the person what the command would do, and you never run `--confirm` or the verb itself. A prepare changes no key, repository, file or Git state; it only records a pending confirmation in Manyhands' data directory (verified by comparing the key list, the repository list, the key files and the repository's Git state before and after). Give the person the exact command to run. `--prepare` never executes, so trying it on an unfamiliar verb is safe. The mechanics of prepare and confirm are in [CLI conventions](cli-conventions.md).

When a step is handed to the person, say which command, why you cannot run it (a passphrase prompt needs their terminal, or the action is destructive), and what you will check afterwards.

## Polling and recovery verbs

Each verb here was run before it was placed in a column.

- Reads, no column: `operation list`, `operation show`, `request show`, `index status`, `poll status` and `remote history`. `remote history` connects to the remote and runs one poll first, with a poll's side effects and no pushing, so it needs the key and the pinned host.
- `poll configure`, `poll pause` and `poll resume` change one stored setting, are reversible and need no preview, so you run them alone.
- `operation resume` re-enters an interrupted operation and writes state, and it has no preview (`not_confirmable`), so you describe what it will do and wait. The one exception: you may resume alone an interrupted operation you can prove you started, meaning it belongs to a request ID you minted and saved ([recovery](../../manyhands-recovery/SKILL.md), "Whose operation is it?"), when the person has already been told about it and has removed the cause, for example a sync refused because the remote had no main branch, once they put one there. A baseline list or a matching item is not proof, and for an operation you cannot prove you started you do not ask for an OK to resume it: show it to the person, who resumes it at their terminal or says explicitly that it is theirs. After a passphrase hand-off the person's rerun, or their own `operation resume` at their terminal, finishes the operation, so the agent has nothing to resume. Never resume an operation that someone else's request holds, one you cannot attribute, one the person has not been told about, or a conflict (it only re-answers the conflict).
- `poll once --retire-completed` and `context retire` remove a completed item's local worktree and branch. They refuse unless retirement is proven safe: the remote no longer has the item's branch, local main holds the completion, nothing on the item's branch is missing from main, and the worktree is clean: no untracked, modified or staged file, and no nested Git repository or unreadable directory inside an ignored one. Ignored files such as `target/` do not stop it on a build with the ignored-files change, and are deleted with the worktree; on an older build they refuse it (from the contract, not run; details in [tickets](../../manyhands-tickets/SKILL.md), "Ignored files in the worktree"). Neither has a preview, so name the item and say what will be removed, then wait.
- `item resolve-history` and `remote resolve-history` change what the repository believes about published history, so they stay with the person. You may run their `--prepare` to show the preview, and never `--confirm`.
